# QA 체크리스트 — 테스트 케이스 · 실행 · 탐색 · 리포트

원리 · 이유는 개념 문서(`../topics/`)에 있다. 상태 누락은 `states.md`, 플랫폼 차이는 `platforms.md`, 상태 코드 · 캐시 · 원인 좁히기는 `api-http.md`, 케이스 고르는 기법 · 테스트 종류 · 원칙은 `testing.md`.

## 1. 테스트 설계 순서

1. **기준 문서 읽기** — 기능 명세 · 화면 기획 · 문구 시트 · design_spec. 문서끼리 다른 곳은 버그가 아니라 「기획 확인」으로 분리
2. **마인드맵으로 쪼개기** — 기능 → 세부 동작 → 끝 가지마다 정상 · 예외 · 경계값
3. **시나리오 → 테스트 케이스**
   - 시나리오 = 무엇을 (사용자 흐름 한 줄: "쿠폰을 적용해 결제한다")
   - 케이스 = 어떻게 (사전 조건 · 절차 · 입력값 · 기대 결과)
   - 한 시나리오에서 여러 케이스: 정상 쿠폰 · 만료 쿠폰 · 최소 금액 미달 · 중복 사용
4. **케이스 고르기** — 입력은 동등 분할(묶음마다 대표값 하나) + 경계값, 조건이 겹치면 결정 테이블, 상태가 바뀌면 상태 전이를 따라감. 조합이 너무 많으면 페어와이즈 (`testing.md` 1장)
5. **우선순위** — 깨지면 큰일 나는 기능(결제 · 로그인 · 데이터 생성)부터 (위험 기반, `testing.md` 1장)
6. **종료 기준** — 치명 · 주요 0건, 핵심 시나리오 전부 통과. 결함 0건이어도 핵심 시나리오의 목적을 못 이루면 통과가 아님. 문서대로인데 목적에 안 맞으면 「기획 확인」 (`testing.md` 5장)
7. **실행 전 준비** — 케이스 사전 조건에 필요한 계정 · 데이터(회원 · 상품 · 쿠폰 등)가 있는지 먼저 확인. 없어서 못 돌린 케이스는 「실행 못함」과 사유 (`testing.md` 4장)
8. **결과 보고** — 수행률(실행한 케이스 / 전체) · 통과율 · 남은 결함을 함께 적고, 종료 기준을 채웠는지로 판정 (`testing.md` 4장). Pass는 "해 본 범위에서 못 찾음"이지 "결함 없음"이 아님 (`testing.md` 5장)

## 2. 테스트 케이스 형식

| ID | 시나리오 | 사전 조건 | 절차 | 입력값 | 기대 결과 | 유형 | 결과 |
|---|---|---|---|---|---|---|---|
| TC-01 | 로그인 | 가입된 계정 | 1. 아이디 · 비밀번호 입력 2. 로그인 | 올바른 값 | 메인 이동 | 정상 | Pass / Fail / 실행 못함 |

- 유형: 정상 / 예외 / 경계값 / 권한 / 비정상 상황
- 누가 실행해도 같은 결과가 나오게 구체적으로
- 참고 규모: 로그인 화면 수십 개, 회원가입 26개 이상

## 3. 반드시 시도할 비정상 상황

| 상황 | 시도 |
|---|---|
| 연타 | 생성 · 저장 · 결제 버튼 빠르게 두 번 |
| 권한 우회 | 권한 없는 화면 주소 직접 입력, 남의 데이터 id로 접근 · 수정 · 삭제 |
| 없는 대상 | 잘못된 id · 삭제한 대상 재진입 |
| 입력값 | 빈 값 · 공백 · 특수문자 · 이모지 · 아주 긴 값 · 경계값 |
| 중단 · 복귀 | 작성 중 뒤로 갔다 오기 · 탭 이동 · 새로고침 |
| 네트워크 | 오프라인 전환 후 저장 · 복구 후 재시도 |
| 화면 | 최소 폭 · 큰 글씨 · 긴 텍스트 · 큰 숫자 · 빈 값 (`states.md` 5장) |
| 상태 | 버튼 누름 · 처리 중 · 비활성 이유, 입력 오류, 로딩 · 빈 결과 · 오류 화면 (`states.md`) |
| OS · 브라우저 | OS와 만나는 화면은 iOS · 안드로이드 따로, 웹은 기반이 다른 브라우저 2개 이상 (`platforms.md`) |
| 반영 | 생성 · 수정 · 삭제 후 목록 · 상세 · 개수 · 검색 |
| 인증 후 변경 | 인증 끝낸 값을 다시 수정 |
| 출시 · 운영 | 점검 상태에서 진입 → 점검 화면, 강제 업데이트 대상 구버전으로 실행 → 안내 (기획에 정의된 경우) |
| 지표 이벤트 | 퍼널 단계마다 이벤트가 찍히는지, A/B 그룹마다 화면 각각, 새로고침 · 백그라운드가 숫자에 어떻게 잡히는지 (이벤트 정의가 있을 때) |

## 4. 탐색적 테스트 세션

- **차터 한 줄**: 무엇을 · 어떤 방법으로 · 무엇을 찾을지 (예: "장바구니를 이상한 수량 입력으로 흔들어 금액 오류를 찾는다")
- 시간 30분 ~ 1시간
- 막막하면 5방향: 경계값 · 이상한 입력 · 중단 후 복귀 · 연타 · 네트워크 끊기
- 한 일과 발견을 시간과 함께 메모 → 그대로 재현 절차가 됨
- 결과: 버그 N건 · 기획 질문 N건 · 새 테스트 케이스 N개. 찾은 시나리오는 케이스로 추가해 다음 회귀에 포함

## 5. 버그 리포트 형식

```
[화면/기능] 무엇을 했을 때 어떻게 됨   ← 제목 한 줄

- 환경: 브라우저 · 뷰포트 / 기기 · OS, 앱 버전 · 빌드 번호 · 커밋
- 심각도: 치명 / 주요 / 보통 / 사소
- 재현 절차: 1. 2. 3.
- 기대 결과: (근거 문서 · 항목)
- 실제 결과:
- 증거: 스크린샷 · 콘솔 로그 · 네트워크 요청
- 원인 위치 추정: 구현 / 기획 · 디자인 확인 필요
```

- 등록 전에 다시 재현해 절차를 확정 (`testing.md` 5장)
- 감정 없이 사실만. "결제가 안 돼요"(X) → 언제 · 어디서 · 어떻게
- 버그인지 스펙인지 애매하면 버그로 등록하지 말고 「기획 확인」으로

### 원인 위치 좁히기

- 화면 값과 응답 JSON을 대조해 프론트 · 서버를 나눈다. 증상별로 먼저 의심할 곳(캐시 · 로드 밸런서 · DNS · SSL · 부하 · 이벤트 로그)은 `api-http.md` 4 · 5장

## 6. 심각도

| 심각도 | 기준 | 예 |
|---|---|---|
| 치명 | 핵심 기능이 아예 안 됨, 데이터 손상 · 보안 | 결제 버튼 누르면 앱 종료, 남의 정보 노출 |
| 주요 | 기능은 되지만 결과가 틀림 | 검색 결과 정렬 오류, 금액 계산 오류 |
| 보통 | 쓸 수는 있지만 불편 | 버튼 글자 잘림 |
| 사소 | 사용에 영향 거의 없음 | 로고 오타 (단, 노출이 크면 우선순위는 높음) |

- 심각도 = 문제의 크기 / 우선순위 = 고칠 순서. 영향 범위 · 노출 · 우회 방법을 근거로 따로 판단

## 7. 결함 상태 흐름

신규 → 배정 → 수정 완료 → **재테스트** → 통과 시 종료 / 실패 시 재오픈. 반려(재현 안 됨 · 중복 · 의도된 동작) · 보류(다음 배포)도 있음. 수정 완료는 끝이 아님 — QA 재테스트 통과가 종료.

## 8. 회귀 테스트

- 새 빌드 · 미리보기를 받으면 본 실행 전에 핵심 기능이 살아 있는지 먼저 (스모크, `testing.md` 3장)
- 고친 곳은 좁고 깊게(새니티) + 연관 기능 · 핵심 흐름(로그인 · 결제 · 데이터 생성) 다시(회귀) (`testing.md` 3장)
- 고친 뒤 들어온 다른 수정도 재확인
- 같은 케이스만 반복하지 않는다. 결함이 몰린 기능 주변과 탐색에서 찾은 시나리오를 케이스로 더한다 (살충제 역설 · 결함 집중, `testing.md` 5장)
- 핫픽스: 고친 곳 + 주변 기능. 롤백: 되돌린 뒤 데이터가 깨지지 않았는지
- 결과는 버전 · 빌드 번호별로 기록. 스테이징에서 할 때는 운영과 설정이 같은지 먼저

## 9. VOC로 우선순위 정하기

기존 서비스를 고치는 작업이고 VOC(문의 · 불만 · 리뷰) 자료가 있을 때만.

- 유형 분류: 오류 / 사용법 / 정책 요청 — 오류만 QA가 재현 확인
- 건수 추이: 배포 다음 날 급증 = 장애 신호 → 그 기능부터 회귀
- 재문의율 높음 = 고쳤다고 했는데 안 고쳐짐 → 재테스트 대상
- 결함 전환율 낮음 = 버그보다 안내 · 문구 문제 → 「기획 확인」으로 (Engineer에게 넘기지 않음)
- 재현 정보: 기기 · 앱 버전을 같이 받으면 재현율이 올라감
- 수정 배포 뒤 만족도(CSAT)로 개선 효과 확인. 리디자인 직후 하락은 변화 거부일 수 있어 한 번이 아니라 추이로 본다 (`flows.md` 6장)
