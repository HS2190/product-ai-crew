# 상태 설계 (버튼 · 입력 · 로딩 · 빈 상태 · 오류 · 끝값)

- 언제 읽나: 컴포넌트 · 화면을 설계할 때(디자이너), 예외 · 정책을 정할 때(기획자), 상태 문구를 쓸 때(UX 라이터), 상태를 구현할 때(Engineer), 상태 누락을 검수 · 테스트할 때(Reviewer · QA)
- 원칙: 시안 한 장이 아니라 **반복해서 쓸 컴포넌트**를 만드는 것. 가장 잘 맞는 예시뿐 아니라 까다로운 예시를 넣어 본다

## 핵심

1. **기본 화면에서 멈추지 않는다.** 누른 뒤 · 기다리는 동안 · 끝난 뒤 · 실패했을 때 · 비어 있을 때를 함께 그린다
2. **눌렸다는 반응과 처리 성공은 다르다.** 두 가지를 따로 설계한다
3. **상태가 바뀌는 조건과 기준값을 적는다.** 그림만 있으면 개발자가 추측한다

## 1. 버튼

| 상태 | 보여 줄 것 |
|---|---|
| 기본 | 처음 보이는 모습. 조작 전 상태도 설계 대상 |
| 누름(프레스드) | 손가락을 댄 동안 색 · 깊이 변화. 성공했다는 뜻은 아님 |
| 처리 중 | 기다리는 중이라는 표시. 이 동안 다시 눌러도 요청은 1번(`../checklists/engineer.md`) |
| 완료 | 결과 안내. 모든 행동에 팝업을 띄우지 말고 상황에 맞는 변화로 |
| 비활성 | 왜 누를 수 없는지 알 수 있게 (입력이 덜 끝남 등) |
| 오류 · 키보드 포커스 | 기기 · 기능에 따라 추가 |

- 눌렀는데 아무 변화가 없으면 사용자는 **또 누른다**. 중복 요청 · 중복 결제가 여기서 생긴다
- 다섯 가지를 모든 버튼에 그대로 넣는 규칙은 아니다. 버튼마다 필요한 상태를 고른다

## 2. 입력칸

| 상태 | 보여 줄 것 |
|---|---|
| 기본(디폴트 · 레스팅) | 아무 조작 전. 무엇을 적는 칸인지(레이블) |
| 포커스 | 선택됨 표시(테두리 등) |
| 입력 중(타이핑) | 커서 · 입력값. 포커스는 유지될 수 있음 |
| 입력됨(타입드) | 다른 곳으로 옮긴 뒤에도 값이 남은 모습 |
| 오류 | 무엇이 틀렸고 어떻게 고치는지. 칸 아래 문구인지 확인 창인지 형태도 정함 |
| 비활성 · 읽기 전용 | 수정할 수 없음이 보이게 |

- 플레이스홀더는 입력하면 사라진다. 입력 뒤에도 필요한 정보(무엇을 적는 칸인지)는 계속 보이는 레이블로 둔다
- 한 줄 입력(텍스트 필드)과 여러 줄 입력(텍스트 영역)은 동작이 다르다. 줄이 늘 때 어떻게 보이는지 정한다
- 같은 오류가 반복되면 같은 문구만 보여 주지 않는다. 몇 번째부터 다음 행동(비밀번호 찾기 등)을 안내할지는 정책

## 3. 로딩 · 진행

| 방식 | 언제 |
|---|---|
| 스켈레톤 | 들어올 내용의 배치를 미리 보여 줄 수 있을 때(목록 · 카드) |
| 로더(회전 표시 등) | 진행 중이라는 사실만 알릴 때 |
| 진행 표시(바 · 원형) | 진행률을 실제로 알 수 있는 작업(업로드 등) |

- 진행률을 알 수 없는 작업에 **임의의 퍼센트를 넣지 않는다**
- 기다림도 설계 대상이다. 처리 중인지, 얼마나 걸리는지, 끝나면 어떻게 알게 되는지를 알려 주면 같은 시간도 다르게 느껴진다(카페 진동벨)
- 스켈레톤은 로딩이 끝나면 사라지고, 데이터가 0건이면 빈 상태로 넘어가야 한다

## 4. 빈 상태

- 목록 화면은 항목이 있을 때만이 아니라 **처음 들어왔을 때 · 불러오는 중 · 오류** 상태가 필요하다
- 없음과 나쁨을 구분한다. 리뷰 없는 새 가게에 별점 0.0을 보여 주면 평가가 나쁘다고 읽힌다 → '신규' 같은 별도 표시
- 별도 표시를 언제 끝낼지(리뷰 N개 · 기간)도 정책으로 정한다
- 빈 상태에는 다음 행동(첫 항목 만들기 · 다른 조건으로 찾기)을 둔다. 검색 · 필터 결과 0건은 처음 비어 있는 상태와 문구가 다르다

## 5. 데이터가 달라질 때 (변수)

| 상황 | 확인 |
|---|---|
| 긴 이름 · 긴 상품명 | 두 줄을 넘을 때 카드 구조 유지, 말줄임 위치 |
| 큰 숫자 | 자릿수가 늘 때 옆 정보와 겹침. 어느 값부터 표기를 바꿀지(예: 9,999+) |
| 큰 금액 | 상품 카드에 1,000만 원을 넣어 본다 |
| 배지 여러 개 · 별점 없음 | 들어올 수 있는 조합을 다 넣어 본다 |
| 항목 수 증가 | 적을 때 쓰던 모양이 많을 때도 읽히는지 (배너 20장에 점 20개 → '3 / 20') |
| 수량 끝값 | 1일 때 빼기, 최대일 때 더하기 · 안내 문구. 최댓값은 재고 · 구매 제한 정책 |

- 케이스는 정책을 낳는다. 장바구니 100개 · 최대 수량 · 반복 오류처럼 화면이 대응해야 하는 상황은 기획 정책으로 이어진다

## 6. 오류 · 없는 대상

- 없는 대상(삭제된 글 · 잘못된 링크) · 서버 오류 · 네트워크 끊김 · 권한 거부 · 로그인 만료 → 빈 화면이나 무한 로딩 대신 안내 + 다음 행동
- 평소엔 안 보이는 화면도 빠지기 쉽다: 서버 점검 화면, 구버전 강제 업데이트 안내(기획에 정의된 경우)
- 저장 실패 시 작성 내용을 잃지 않게

## 7. 문서에 남길 것

1. 구현할 내용: 어떤 요소 · 상태가 있는지
2. 동작: 무엇을 하면 어떤 상태로 바뀌는지, 선택 안 했을 때는 어떤지
3. 정책 · 기준값: 최댓값, 반복 횟수, 표기가 바뀌는 값, 별도 표시를 끝내는 조건
4. 설계 의도: 왜 그렇게 했는지

- 시안을 넘긴 뒤 "목록이 비어 있으면요?", "저장에 실패하면요?"라는 질문이 오면 설명할 조건이 남아 있는 것

## 역할별로 쓰는 법

- **기획자:** 기능 명세에 상태 목록과 바뀌는 조건, 기준값(최대 · 반복 횟수 · 표시 기준)을 적는다
- **디자이너:** 컴포넌트마다 필요한 상태를 고르고 화면에 그린다. 변수 표의 까다로운 값을 대표 화면에 넣어 본다
- **UX 라이터:** 비활성 이유, 오류 원인과 고치는 법, 빈 상태의 다음 행동, 처리 중 · 완료 안내 문구를 상태마다 쓴다
- **Engineer:** 누름과 처리 결과를 분리 구현, 처리 중 중복 요청 차단, 기준값을 스펙 그대로
- **QA · Reviewer:** 상태 목록과 실제 화면을 대조하고, 변수 표의 값을 넣어 본다
