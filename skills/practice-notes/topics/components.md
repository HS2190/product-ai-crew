# 컴포넌트 이름사전 (이름 · 동작 · 문서에 남길 것)

- 언제 읽나: 컴포넌트를 고르거나 스펙을 쓸 때(디자이너), 컴포넌트를 구현할 때(Engineer), 스펙에 동작이 빠졌는지 볼 때(Reviewer)
- 원칙: 이름을 맞추는 게 목적이 아니다. **이름과 함께 동작 · 상태 · 기준값을 문서에 남기는 것**이 목적. 같은 이름도 팀 · 디자인 시스템마다 뜻이 조금씩 다르므로, 회사 디자인 시스템의 명칭이 있으면 그것이 우선

## 핵심

1. 모양이 같으면 사용자는 **같은 동작을 기대한다.** 겉모양이 같은데 동작이 다르면 눌러 봐야 안다
2. "얼럿", "피커"처럼 이름만 적으면 팀원마다 다른 것을 떠올린다. **역할 + 형태 + 동작**을 함께
3. 제스처는 **손가락 동작과 화면 결과를 함께** 적는다

## 1. 표시 · 선택

| 이름 | 무엇 | 문서에 남길 것 |
|---|---|---|
| 배지 | 아이콘 옆 작은 점 · 숫자 · 문자 | 무엇을 세는지(안 읽음 / 새로 추가), 언제 나타나고 사라지는지, 본 뒤 어디를 확인하면 되는지 |
| 칩 | 누르면 선택이 바뀌는 둥근 요소(필터 등) | 선택 가능 여부, 선택 후 변화, 여러 개 선택 가능한지 |
| 레이블 | 상태 · 속성을 보여 주는 표시 | 누를 수 있는지. 칩과 모양이 같으면 구분 방법 |
| 토글 | 켜짐 · 꺼짐 스위치 | 항목 이름은 옆에, 상태는 손잡이 위치 · 대비로. 색 하나로만 구분 금지, 보조 기술에 이름 · 상태 전달 |
| 스테퍼 | 수량을 한 단계씩 바꾸는 +/− | 최소 · 최대에서의 모습, 상품 정보 묶음 안에서 읽히는지. 단계 진행 표시(스텝 인디케이터)와 용도 구분 |
| 피커 | 정해진 후보 중 값을 고름(휠 · 달력) | 선택할 값, 가능한 범위, 처음 보여 줄 값. 날짜인지 일반 값인지 |
| 아바타 그룹 | 프로필 사진을 겹쳐 놓음 | 존재만 알릴지 특정 사람을 구분해야 하는지, 넘치면 '+N' |
| 페이지 표시 | 배너 아래 점 · 바 · 숫자 | 운영할 장수에 맞춰 고름(많으면 '3 / 20'), 숫자만이면 넘기는 방법이 보이는지 |

## 2. 입력

| 이름 | 무엇 | 문서에 남길 것 |
|---|---|---|
| 텍스트 필드 | 한 줄 입력 | 글자 수 상한, 입력 형식, 상태(`states.md`) |
| 텍스트 영역 | 여러 줄 입력 | 줄이 늘 때 높이가 늘어나는지 · 스크롤인지, 상한 |
| 플레이스홀더 | 입력하면 사라지는 연한 안내 | 사라져도 되는 힌트만. 칸 이름은 레이블로 |

## 3. 알림 · 겹쳐 뜨는 요소

| 이름 | 문서에 남길 것 |
|---|---|
| 얼럿 | 역할(주의 알림)과 형태를 함께: 입력칸 아래 문구인지, 확인 버튼이 있는 창인지. 어디에 뜨고 어떤 확인이 필요한지 |
| 토스트 | 표시 시간, 여러 개가 뜰 때 겹치지 않는지 |
| 모달 | 바깥 탭 · 뒤로 가기로 닫히는지, 닫은 뒤 돌아갈 위치 |
| 바텀 시트 | 끌어내려 닫기, 키보드가 올라올 때 가려지지 않는지 |
| 딤 | 모달 뒤 어두운 반투명 막. 정해진 불투명도 수치는 없음. 모달과 뒤 화면을 한 장면으로 보고 구분되는지 |
| 드롭다운 | 항목이 많을 때 스크롤 · 잘림 |
| 툴팁 | 모바일에서 어떻게 띄우는지, 화면 밖 잘림 |

- **레이어(Z축):** 배경 → 딤 → 바텀 시트 · 팝업처럼 앞뒤가 있다. 앞뒤 순서, 누를 수 있는 영역, 닫으면 어디로 돌아가는지 정한다. 여러 페이지를 이동하는 탐색 단계와 한 화면 안에서 겹치는 레이어는 구분해서 생각

## 4. 탐색 · 구조

| 이름 | 문서에 남길 것 |
|---|---|
| 앱 바 · 헤더 | 화면별로 브랜드(로고)가 필요한지 현재 위치(제목 · 뒤로 가기 · 검색)가 필요한지. 홈은 브랜드, 상세는 제목 |
| 탭 | 탭 이동 후 스크롤 위치 · 입력값 유지 |
| 아코디언 | 하나만 열지 여러 개를 열어 둘지(비교가 필요하면 여러 개), 펼침 · 접힘 구분 |
| 캐러셀 | 마지막 장에서 처음으로 가는지, 자동 넘김 여부 |
| 스켈레톤 · 로더 · 진행 표시 | `states.md` 3장 |

## 5. 제스처

| 이름 | 무엇 | 문서에 남길 것 |
|---|---|---|
| 프레스 · 프레스드 | 누르는 동작 · 누르는 동안의 모습 | 누르는 중과 손을 뗀 뒤. 처리 결과와 별개 |
| 롱 프레스 | 누른 채 잠시 유지(편집 · 복사 연결) | 길게 누른 뒤 무엇을 할 수 있는지 보이는지. 숨은 동작에만 필수 기능을 두지 않기 |
| 핀치 아웃 · 줌 인 | 두 손가락을 벌림 · 그 결과 확대 (반대는 핀치 인 · 줌 아웃) | "두 손가락을 벌리면 지도를 확대"처럼 동작 + 결과 |
| 드래그 | 손가락을 댄 채 움직이는 동안 따라옴 | 방향, 놓았을 때 위치 |
| 플릭 | 짧게 튕긴 뒤에도 이어서 넘어감 | 방향, 손을 뗀 뒤 멈추는 위치. "부드럽게"로는 전달 안 됨 → 프로토타입 · 참고 영상 |
| 스와이프 | 밀어서 넘기기 · 지우기 | iOS 왼쪽 가장자리 스와이프는 뒤로 가기와 겹침(`platforms.md`) |

## 6. 컴포넌트 이름을 정리할 때

- 이름만 붙이지 말고 선택 가능 여부와 선택 후 변화까지 적어 두면 구현에서의 오해가 준다
- 이름을 억지로 쪼개지 않는다(디폴트 vs 레스팅처럼 팀마다 겹치는 구분). 대신 기본 화면에서 무엇이 보이고 조작하면 무엇이 바뀌는지를 적는다
- 두 번 이상 나오는 덩어리는 컴포넌트로 만들고, 화면에서 직접 그리지 않는다

## 역할별로 쓰는 법

- **디자이너:** `component_spec`의 컴포넌트마다 위 표의 「문서에 남길 것」을 채운다
- **Engineer:** 스펙에 동작이 빠졌으면 추측하지 말고 `implementation_notes`에 정한 내용을 남긴다
- **Reviewer:** 모양이 같은데 동작이 다른 요소가 섞이지 않았는지, 겹쳐 뜨는 요소의 닫기 · 복귀가 정해졌는지
