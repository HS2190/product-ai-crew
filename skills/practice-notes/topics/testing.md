# 테스트 설계 · 종류 (케이스 고르는 기법 · 범위 · 목적별 종류)

- 언제 읽나: 테스트 케이스를 고를 때 · 재테스트 범위를 정할 때(QA), 조건 조합 · 상태 변화가 있는 기능을 명세할 때(기획자), QA 산출물을 검수할 때(Reviewer)
- 원칙: 케이스를 많이 쓰는 게 목표가 아니다. **빠짐없이, 그러나 겹치지 않게** 고르는 게 목표

## 핵심

1. 케이스는 기법으로 고른다. 같은 결과를 내는 값은 묶고, 결과가 바뀌는 끝값 · 조합 · 상태 변화를 집중해서 본다
2. 테스트는 **범위**(단위 · 통합 · E2E)와 **목적**(스모크 · 새니티 · 회귀 등)이 다르다. 지금 무엇을 확인하려는지부터 정한다
3. 위험한 곳부터. 깨졌을 때 피해가 큰 기능을 먼저 본다

## 1. 케이스를 고르는 기법

| 기법 | 하는 일 | 크루에서 쓰는 곳 |
|---|---|---|
| 경계값 분석 | 끝값 주변을 테스트 | "8~16자"면 7 · 8 · 16 · 17자처럼 경계 양쪽 (`../checklists/planner.md` 1장) |
| 동등 분할 | 같은 결과가 나오는 값끼리 묶어 묶음마다 하나씩만 | 유효 · 무효 입력을 묶음별 대표값 하나로. 같은 묶음의 값을 여러 개 넣어도 새로 알게 되는 것이 없음 |
| 결정 테이블 | 조건 조합마다 나오는 결과를 표로 | 회원 여부 × 쿠폰 만료 여부 → 4가지 결과 (`planner.md` 1장) |
| 상태 전이 | 상태가 바뀌는 길을 따라감 | 주문 · 배송처럼 상태가 바뀌는 기능. "배송 중에는 취소 불가" 같은 막힌 길까지 (`planner.md` 1장) |
| 페어와이즈 | 두 개씩 짝만 맞춰 조합 수를 줄임 | 조건 · 설정이 많아 전체 조합을 다 돌릴 수 없을 때 |
| 위험 기반 | 위험한 곳부터 먼저 테스트 | 결제 · 로그인 · 데이터 생성 우선 (`../checklists/qa.md` 1장) |

- 커버리지는 테스트가 지나간 코드 비율. 크루 QA는 코드가 아니라 기준 문서로 케이스를 만들므로, 기능 명세의 예외 · 상태 · 기준값을 얼마나 다뤘는지로 빈틈을 본다

## 2. 범위: 단위 · 통합 · E2E

| 범위 | 무엇을 | 성격 |
|---|---|---|
| 단위 | 함수 하나만 떼어서 확인 | 가장 작고 가장 빠름. 가장 많이 둠 |
| 통합 | 여러 부분을 연결해서 확인 (요청이 서버를 거쳐 DB에 잘 저장되는지) | 연결 부분을 봄 |
| E2E | 사용자처럼 처음부터 끝까지 (로그인부터 결제까지) | 핵심 흐름만 |

- **테스트 피라미드:** 아래(단위)를 가장 많이, 위(E2E)로 갈수록 적게
- **V 모델:** 만드는 단계마다 짝이 되는 테스트가 있다
- **크루에서:** QA의 Playwright 실행은 E2E에 해당. 서버 · DB 연결(통합)은 mock이라 검증 범위 밖. 회귀 때 다시 돌릴 스크립트는 핵심 흐름부터 갖춘다

## 3. 목적별 테스트 종류

| 종류 | 확인하는 것 | 크루에서 |
|---|---|---|
| 스모크 | 새 빌드의 핵심 기능이 살아 있는지 빠르게 | 미리보기를 받으면 본 실행 전에 먼저 |
| 새니티 | 고친 부분만 좁고 깊게 | 재테스트(`retest_of`)에서 고친 버그 |
| 회귀 | 수정 후 기존 기능이 그대로인지. 고친 곳 주변까지 | 재테스트에서 연관 기능 · 핵심 흐름 (`qa.md` 8장) |
| 탐색 | 시나리오 없이 직접 써 보며 버그 찾기 | 탐색 세션 (`qa.md` 4장) |
| 인수 | 고객 · 기획 기준으로 출시해도 되는지 | 기대 결과의 근거를 기준 문서에 둠. `qa_status` 판정 |
| 알파 · 베타 | 회사 안에서(알파) / 실제 사용자가(베타) 미리 써 봄 | 범위 밖 |
| 성능 | 응답 속도가 얼마나 빠른지 측정 | 서버 응답은 mock이라 범위 밖 |
| 부하 | 사용자가 몰려도 버티는지 | 범위 밖 |
| 호환성 | 여러 기기 · 브라우저에서 똑같이 되는지 | OS · 브라우저 시도 (`qa.md` 3장, `platforms.md`) |
| 사용성 | 사용자가 헤매지 않고 쓸 수 있는지 | 디자인 단계의 가상 사용자 점검 |
| 접근성 | 화면 읽기 프로그램 · 큰 글씨로도 쓸 수 있는지 | 큰 글씨 · 최소 폭 시도 (`qa.md` 3장, `size-units.md` 6장) |
| 보안 | 권한 없이 접근하거나 정보가 새는 곳 | 화면 쪽은 권한 우회 시도 (`qa.md` 3장) |

- 결함이 등록부터 종료까지 거치는 흐름(결함 생명주기)은 `qa.md` 7장

## 역할별로 쓰는 법

- **QA:** 입력은 동등 분할 + 경계값, 조건이 겹치면 결정 테이블, 상태가 바뀌면 상태 전이로 케이스를 고른다. 새 빌드는 스모크부터, 재테스트는 새니티(고친 곳) + 회귀(주변 · 핵심 흐름)
- **기획자:** 결정 테이블 · 상태 전이 규칙을 기능 명세에 남기면 그대로 테스트 케이스가 된다
- **Reviewer:** 같은 묶음의 값만 반복하지 않는지, 경계 · 조합 · 상태 변화 케이스가 빠지지 않았는지, 재테스트에 고친 곳과 주변 회귀가 모두 있는지
