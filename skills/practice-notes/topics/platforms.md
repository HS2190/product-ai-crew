# 플랫폼 (웹 · 앱 · 네이티브 · 웹뷰 · iOS와 안드로이드)

- 언제 읽나: 플랫폼(`platform`: mobile / web / both)을 정하고 화면을 나눌 때(기획자 · 디자이너), 화면 방식(네이티브 · 웹뷰)과 브라우저 지원 범위를 정할 때(Engineer), 테스트 환경을 정할 때(QA)
- 원칙: 화면 크기만 다른 게 아니다. **조작 방식 · 운영체제 · 화면 방식**이 다르면 같은 기능도 다르게 움직인다

## 핵심

1. 서비스가 **어디 위에서 돌아가는지**(OS · 브라우저 · 앱 안 웹뷰)부터 정한다
2. 화면마다 **네이티브인지 웹뷰인지** 적는다. 수정 반영 방식과 확인할 것이 다르다
3. OS와 만나는 화면(뒤로 가기 · 권한 · 키보드 · 날짜 선택 · 공유)은 **iOS와 안드로이드를 따로** 확인한다

## 1. 운영체제와 서비스 형태

| 형태 | 특징 | 판단할 것 |
|---|---|---|
| PC 웹 | 마우스 · 트랙패드, 넓은 화면, 호버 있음 | 브라우저 폭 변화, 키보드 조작 |
| 모바일 웹 | 손가락, 브라우저 주소창 · 하단 바가 화면을 차지 | 터치 영역, 브라우저마다 다른 하단 영역 |
| 앱 | OS 기능(푸시 · 카메라 · 권한) 사용, 스토어 배포 | 스토어 심사 · 업데이트 주기, OS별 차이 |

- 반응형: 브라우저 폭에 따라 같은 화면의 구성이 연속으로 바뀐다
- 적응형: 플랫폼 · 기기별로 따로 설계한 화면을 보여 준다
- 어느 쪽이든 PC는 마우스, 모바일은 손가락이라는 조작 차이를 함께 본다(호버 상태 · 터치 크기)

## 2. 네이티브 · 하이브리드 · 웹뷰

- **네이티브:** iOS · 안드로이드용으로 각각 만든 화면. 고치려면 앱 업데이트(스토어 심사)가 필요
- **웹뷰:** 앱 안에서 웹 페이지를 띄우는 창. 웹만 고치면 앱 업데이트 없이 바로 반영
- **하이브리드:** 두 방식을 섞은 앱. 큰 서비스일수록 섞어 쓰는 경우가 많다(웹뷰 영역만 따로 배포해 배포 시간을 크게 줄인 사례도 있음)
- 웹뷰 화면에서 꼭 볼 것: 뒤로 가기, 로딩 표시, 로그인 유지, 네이티브와 주고받는 데이터
- 외부 결제: 인앱(결제 앱으로 넘어갔다 돌아옴)은 앱 미설치 시 스토어 안내 · 앱이 꺼져도 결과 수신, 웹뷰(앱 안 결제창)는 다시 로그인 요구가 없는지 · 카드사 앱 호출이 막히지 않는지 · 닫기와 뒤로 가기. 마지막엔 서버 기록과 화면 결과가 같은지

## 3. iOS와 안드로이드 차이

| 항목 | iOS | 안드로이드 | 확인 |
|---|---|---|---|
| 뒤로 가기 | 왼쪽 가장자리 스와이프 | 제스처 · 시스템 버튼 | 두 방식 모두 같은 화면으로 가는지, 앱이 갑자기 꺼지지 않는지 |
| 위치 권한 | 한 번만 허용 · 앱 사용 중 허용 | 비슷하지만 모양 · 선택지가 다름 | '한 번만 허용' 뒤 다음에 다시 묻는지, 거부 시 안내 |
| 알림 권한 | 앱이 요청 | 13 이상은 앱이 요청, 그 아래는 기본 허용 | 버전을 나눠 확인 |
| 키보드 | 기기 · 키보드 앱마다 높이 다름 | 같음. 15 이상은 화면 끝까지 그리는 방식이 기본이라 가려짐 주의 | 입력창 · 저장 버튼이 가려지지 않는지 |
| 날짜 선택 | 달력 또는 휠 | 달력 창 | 저장 형식이 같은지 |
| 공유 창 | OS 공유 시트 | OS 공유 시트(모양 다름) | 받은 쪽에서 링크가 제대로 열리는지 |
| 기본 글꼴 | SF Pro 계열 | Roboto · Noto 계열 | 같은 문구도 줄바꿈이 달라짐 |

## 4. 모바일 앱에서 꼭 볼 것

- 화면을 돌려도 · 앱을 내렸다 다시 열어도 입력한 내용이 남는지
- 네트워크가 끊겼다 돌아오면 다시 시도할 수 있는지
- 작은 화면 · 노치 기기에서 잘리지 않는지(시스템 영역은 `size-units.md`)
- 업데이트 후에도 로그인 · 데이터가 남는지
- 푸시 알림을 누르면 맞는 화면으로 가는지(딥링크)

## 5. 웹에서 꼭 볼 것

- **브라우저 하나로 끝내지 않는다.** 기반이 다른 브라우저를 함께 본다: 크롬 · 웨일 · 엣지(크로미움 계열)와 사파리(웹킷). 아이폰의 모든 브라우저는 웹킷 기반이라 모바일 사파리 확인이 특히 중요
- 오래 둔 뒤 저장해도 작성한 내용이 남는지(세션 만료)
- 주소의 번호만 바꿔도 남의 정보가 보이지 않는지(권한)
- 작은 화면에서 버튼이 가려지지 않는지
- 데이터가 많아도 빨리 뜨고 로딩 표시가 있는지
- 고쳤는데 화면이 그대로면 캐시부터(`api-http.md`)

## 우리 기준과 다를 때

- 회사 conventions에 지원 브라우저 · OS 버전 · 기기 목록이 있으면 그 범위가 테스트 · 디자인 기준이다
- 크로스 플랫폼 프레임워크(Flutter 등)는 한 코드로 두 OS를 그리지만 뒤로 가기 · 권한 · 키보드 같은 OS 동작 차이는 그대로 남는다

## 역할별로 쓰는 법

- **기획자:** 화면 기획안에 화면마다 네이티브 · 웹뷰를 적고, OS별로 갈리는 흐름(권한 · 뒤로 가기)을 표시
- **디자이너:** 플랫폼별 화면 크기 · 시스템 영역 · 조작 방식을 반영하고, OS 차이가 나는 화면은 두 버전을 보여 준다
- **Engineer:** 지원 브라우저 · OS 범위를 `implementation_notes`에 적는다
- **QA:** OS와 만나는 화면은 iOS · 안드로이드를 따로, 웹은 기반이 다른 브라우저 2개 이상
