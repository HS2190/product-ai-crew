# Product AI Crew — 사용 가이드

Claude Code 기반 멀티 에이전트 제품 조직 시스템.
Researcher → PM → 기획자 → 디자이너 → UX라이터 → Engineer 6개의 AI 에이전트가 오케스트레이터의 지휘 아래 순차 실행되고, 각 단계 산출물은 Reviewer의 내용 품질 검수를 거친다. 리서치부터 동작하는 프론트엔드 구현까지가 범위다.

---

## 에이전트 구성

| 에이전트 | 파일 | 하는 일 |
|---------|------|--------|
| 오케스트레이터 | `../CLAUDE.md` | 요청 분석 → 모드 판단 → 에이전트 순차 호출 |
| Researcher | `researcher/CLAUDE.md` | 리서치 수집·종합, 경쟁 분석, insights 도출 |
| PM | `pm/CLAUDE.md` | 비즈니스 목표 정의, PRD 작성, 기능 우선순위 결정 |
| 서비스 기획자 | `planner/CLAUDE.md` | 화면 기획, 기능 명세서, User Flow 설계 |
| UI/UX 디자이너 | `designer/CLAUDE.md` | 화면 디자인, 컴포넌트 스펙, Figma 반영 |
| UX 라이터 | `ux-writer/CLAUDE.md` | UX 문구 작성, 라이팅 가이드, 금지 표현 관리 |
| Engineer | `engineer/CLAUDE.md` | 프론트엔드 구현, 빌드 검증 (최종 산출물) |
| Reviewer | `reviewer/CLAUDE.md` | 각 단계 산출물의 내용 품질 비평 (pass/revise/escalate) |

## 실행 모드

| 모드 | 언제 쓰는가 | 에이전트 순서 |
|------|-----------|-------------|
| **FULL** | 기능을 아무것도 없는 상태에서 구현까지 만들 때 | Researcher → PM → 기획자 → 디자이너 → UX라이터 → Engineer |
| **PLAN** | 리서치·PRD·기획서까지 필요할 때 | Researcher → PM → 기획자 |
| **RESEARCH** | 리서치·경쟁사 분석만 필요할 때 | Researcher 단독 |
| **DESIGN** | 기획안이 이미 있고 디자인만 필요할 때 | 기획자 → 디자이너 |
| **BUILD** | 디자인 스펙·문구가 있고 구현만 필요할 때 | Engineer 단독 (또는 디자이너 → Engineer) |
| **WRITE** | 화면은 완성됐고 문구만 정리할 때 | UX라이터 단독 |
| **CUSTOM** | 원하는 에이전트를 직접 조합할 때 (Researcher·Engineer 포함) | 사용자 정의 |

## 모드별 사용 방법

### FULL 모드 — 전체 프로세스

**상황:** 새 기능을 처음부터 완성까지 만들어야 할 때

```
"[서비스명] 앱에 [기능명] 기능을 새로 만들려고 해.
 기획부터 UX라이팅까지 전부 해줘."

"[서비스명] [기능명] 전체 프로세스 진행해줘."
```

**실행 흐름:**

각 단계 산출물은 **존재 검증 → Reviewer 검수** 2단계 게이트를 통과해야 다음 단계로 넘어간다.

```
Researcher
 └─ 리서치 종합, 경쟁 분석, key_insights 도출
        ↓ [존재 검증] → [Reviewer 검수] (pass/revise/escalate)
PM
 └─ PRD 작성, 기능 우선순위 정의 (리서치 insights 인용)
        ↓ [존재 검증] → [Reviewer 검수] (pass/revise/escalate)
기획자
 └─ 화면 기획안, 기능 명세서, User Flow 작성
        ↓ [존재 검증] → [Reviewer 검수]
디자이너
 └─ 디자인 스펙, 컴포넌트 스펙, Figma 반영
        ↓ [존재 검증] → [Reviewer 검수]
UX라이터
 └─ 화면별 문구 시트, UX라이팅 가이드 작성
        ↓ [존재 검증] → [Reviewer 검수]
Engineer
 └─ 동작하는 프론트엔드 코드, 빌드 결과 (최종 산출물)
        ↓ [존재 검증] → [Reviewer 검수]
완료 보고
```

**산출물:** `workspace/[서비스명]/researcher/`, `pm/`, `planner/`, `designer/`, `ux-writer/`, `engineer/` 각 폴더에 저장 (최종 산출물은 `engineer/`의 동작하는 코드)

---

### RESEARCH 모드 — 리서치만

**상황:** PRD를 쓰기 전에 근거(경쟁사·사용자 데이터)를 먼저 모아야 할 때, 또는 독립적으로 리서치만 필요할 때

```
"[기능명] 관련 경쟁사 분석해줘."

"기존 사용자 피드백 종합해서 인사이트 뽑아줘."

"인터뷰 전사 정리해서 themes/insights로 종합해줘. [자료 경로]"
```

Researcher가 `user-research`·`research-synthesis` 스킬을 활용해 themes → insights → opportunities를 종합한다. 결과는 PM이 `research_path`로 이어받아 PLAN/FULL로 확장할 수 있다.

**산출물:** 리서치 종합 문서 (`workspace/[서비스명]/researcher/research-synthesis-v1.0.md`)

---

### PLAN 모드 — 리서치 + 기획까지

**상황:** 개발 일정이 촉박해서 리서치 근거와 기획 방향만 먼저 잡아야 할 때

```
"[서비스명] [기능명] 기능
 PRD랑 화면 기획서까지만 만들어줘."

"[기능명] 기획서 만들어줘. 디자인은 아직 안 해도 돼."
```

**산출물:** 리서치 종합, PRD, 화면 기획안, 기능 명세서

---

### DESIGN 모드 — 디자인만

**상황:** 기획안이 이미 있고 디자인 작업만 필요할 때

```
"기획안 있어, 디자인만 해줘."

"기획안은 이미 있어. 화면 기획 검토하고 디자인만 완성해줘."
```

**산출물:** 디자인 스펙, 컴포넌트 스펙, Figma 반영 결과

---

### BUILD 모드 — 구현만

**상황:** 디자인 스펙·컴포넌트 스펙·문구가 이미 있고 동작하는 프론트엔드 코드만 필요할 때

```
"디자인 스펙 있어, 코드로 구현만 해줘."

"이 컴포넌트 스펙이랑 문구로 React 화면 만들어줘."

"[Figma URL] 이 디자인 그대로 동작하는 코드로 구현해줘."
```

Engineer가 `frontend-design`·`react-components`·`impeccable` 등 스킬을 활용해 React(기본 Vite+TS) 코드로 구현하고, 빌드 통과·미리보기로 스펙 일치를 자가 확인한다. 데이터는 mock/정적으로 처리하며 백엔드는 범위 밖이다.

**산출물:** 동작하는 프론트엔드 코드 (`workspace/[서비스명]/engineer/`)

---

### WRITE 모드 — UX라이팅만

**상황:** 피그마 화면은 완성됐고 문구만 정리해야 할 때

```
"로그인 화면이랑 [화면명] UX 문구 전체 검토하고
 가이드에 맞게 수정안 만들어줘."

"[Figma URL] 이 화면 문구 작성해줘."

"에러 메시지 가이드에 맞게 전부 수정해줘."
```

**산출물:** 화면별 문구 시트 (원문 / 수정안 / 수정 이유 표 형식) + UX라이팅 가이드

---

### CUSTOM 모드 — 직접 조합

**상황:** 순서나 조합을 직접 정하고 싶을 때

```
"CUSTOM 모드로 PM이랑 UX라이터 병렬로 실행해줘.
 PM은 브랜드 방향성 정의, UX라이터는 보이스 가이드 초안 작성해줘."

"CUSTOM 모드로 기획자 → 디자이너를 3회 반복 실행해줘."
```

**병렬 실행은 Claude Code Task 툴로 동작함**
각 에이전트가 독립적인 서브에이전트로 호출되어 동시에 실행됨.
각 Task에 필요한 인풋을 명시적으로 전달해야 함 (대화 이력 공유 없음).

**병렬 실행 가능한 조합** (의존성 없는 경우만):

| 조합 | 설명 |
|------|------|
| PM + UX라이터 | PM은 PRD, UX라이터는 기존 화면 문구 검토 |
| 기획자 + UX라이터 | 기획자는 신규 화면, UX라이터는 기존 화면 정비 |

**반드시 순서 보장이 필요한 조합:**

| 순서 | 이유 |
|------|------|
| PM → 기획자 | 기획자는 PRD를 인풋으로 받아야 함 |
| 기획자 → 디자이너 | 디자이너는 화면 기획안을 인풋으로 받아야 함 |
| 디자이너 → UX라이터 | UX라이터는 디자인 화면을 인풋으로 받아야 함 |

## 에이전트 직접 호출 (SOLO 모드)

오케스트레이터를 거치지 않고 특정 에이전트와 직접 대화하고 싶을 때.

```
"UX라이터로서 이 문구 검토해줘."
"디자이너 관점에서 이 화면 피드백 해줘."
"PM 입장에서 이 기능의 우선순위를 어떻게 봐?"
```

SOLO 모드에서는 자유롭게 인터랙션하며 유연하게 작업한다.
인풋/아웃풋 형식을 엄격히 따르지 않아도 된다.

**1위 — WRITE 모드**

**3위 — CUSTOM 모드 (PM + UX라이터 병렬)**

두 에이전트가 독립적으로 작업해서 시간 절약.
새 서비스 론칭 초기 기획 단계에 유용.

## 주의사항 및 팁

### 잘못 사용하기 쉬운 케이스

**의존성 있는 에이전트를 병렬로 요청하면 안 됨**
기획자+디자이너는 기획안이 먼저 나와야 디자인이 가능.
이 조합은 병렬 불가, 반드시 순서 지정.

```
✗ "기획자랑 디자이너 동시에 실행해줘"
✓ "기획자 → 디자이너 순서로 실행해줘"
```

**blocked 상태 발생 시 자동으로 다음 단계가 실행되지 않음**
에이전트가 `blocked`를 반환하면 오케스트레이터가 멈추고 사유를 알려줌.
추가 정보를 주거나 작업 범위를 조정한 다음 재호출해야 함.

**Engineer는 디자인 스펙을 *구현*할 뿐 새로 디자인하지 않음**
스펙에 없는 결정은 `implementation_notes`에 남기고, 중대한 경우 디자이너에 확인(blocked).
따라서 스펙이 부실하면 구현 품질도 떨어진다 — 디자이너 단계의 완성도가 최종 구현 품질을 좌우함.
또한 이 시스템의 구현 범위는 프론트엔드까지다(백엔드·DB·API는 mock/정적 데이터로 처리).

**각 에이전트 아웃풋은 2단계 게이트를 통과해야 다음 단계로 넘어감**
산출물은 두 단계를 차례로 거친다.
- **1단계 — 존재 검증**: 필수 항목(파일 존재 여부, 필드 누락 등)을 자동 검증함. 실패 시 `blocked`로 처리하고 누락 항목을 사용자에게 보고함.
- **2단계 — Reviewer 내용 비평**: 존재 검증을 통과하면 Reviewer가 산출물의 *내용 품질*을 비평함. "있는지"가 아니라 "좋은지"를 본다.
  - `pass` → 다음 단계로 진행
  - `revise` → 같은 에이전트가 피드백을 받아 재작업 (같은 산출물 **최대 2회**)
  - `escalate` → 2회 재작업으로도 미흡하거나 방향 자체가 어긋난 경우. 작업을 멈추고 **사용자 판단**을 요청함.

재작업 횟수는 `session.md`에 기록되어, 대화가 끊겨 재개해도 2회 상한이 유지됨.

**작업 도중 대화가 끊겨도 이어서 진행 가능**
오케스트레이터는 각 에이전트 완료 시마다 `workspace/[서비스명]/session.md`에 진행 상태를 기록함.
같은 작업을 다시 요청하면 "이어서 진행할까요?" 확인 후 멈춘 단계부터 재개함.

### 더 잘 활용하는 방법

**컨텍스트를 구체적으로 줄수록 산출물 퀄리티가 높아짐**

```
✗ "기능 만들어줘"
✓ "[서비스명] 앱, 작업자/관리자 같은 역할 기준, 현장에서 스마트폰으로 사진 촬영 후
   등록하는 기능 만들어줘. 한 손 조작, 큰 버튼, 최소 입력 고려해줘."
```

**기존 리서치 자료가 있으면 Researcher에 함께 넘기기**
인터뷰 전사·설문 결과·지원 티켓 같은 기존 자료가 있으면 Researcher에 `research_input`으로 함께 넘긴다.
가용한 실제 데이터가 많을수록 근거 품질이 올라가고, PM의 문제 정의도 추측이 아니라 사실 위에서 시작된다.
자료가 없으면 Researcher가 경쟁사 분석·웹 검색·페르소나 범위에서 수행하되 한계를 명시한다.

**피그마 MCP 활용**
디자이너 에이전트는 피그마 MCP가 연결되어 있으면 피그마 파일을 직접 열고 읽고 수정.
피그마 URL만 공유하면 별도 스크린샷 없이 바로 작업 가능.

**산출물 저장 위치**
모든 산출물은 자동으로 `workspace/[서비스명]/` 하위에 저장됨.
이 폴더는 `.gitignore` 처리되어 있어 로컬에만 유지됨.

## 프로젝트 간 기억층 — 쓸수록 똑똑해짐

`session.md`가 한 프로젝트 *안*의 진행을 기억한다면, `workspace/_memory/`는 프로젝트를 *넘어* 누적되는 맥락을 기억한다. 시스템이 쓸수록 그 회사·그 디자이너에게 맞게 똑똑해지는 인프라다.

**자동 주입 (읽기)** — 작업 시작 시 오케스트레이터가 개인 프로파일과 해당 회사의 기억(결정·컨벤션)을 자동 로딩해 모든 에이전트에 `memory_context`로 주입한다. 사용자가 매번 "지난번 결정 참고해"라고 말하지 않아도 적용된다.

**반자동 누적 (쓰기)** — 자동 저장하지 않는다. 기억할 가치가 있는 결정·선호가 나오면 오케스트레이터가 *제안*하고, 사용자가 *승인한 것만* 누적된다.

**2층 구조 / 회사 분리**
- 개인 층(`designer-profile.md`): 회사 불문 유지되는 나의 작업 취향.
- 회사 층(`companies/[회사명]/`): 회사별로 분리 — A사의 결정이 B사로 새지 않는다.

**넣지 않는 것** — 산출물(PRD·디자인·코드), 리서치 원본 데이터, 일회성 정보, 세션 진행 상태는 기억층에 넣지 않는다. 기억층은 **판단과 선호**만 담는다.

> 페르소나(`persona.md`)와는 다른 층이다. 페르소나 = 이 프로젝트의 *사용자가 누구인가*, 기억층 = 이 회사/디자이너가 *어떻게 일하는가*.

## 산출물 저장 경로 참고

```
workspace/
├── _memory/          ← 프로젝트 간 기억층 (개인 프로파일 + 회사별 결정·컨벤션)
│   ├── designer-profile.md
│   └── companies/[회사명]/{decisions,conventions}.md
└── [서비스명]/
    ├── researcher/    ← 리서치 종합, 경쟁 분석, insights
    ├── pm/            ← PRD, 로드맵, 기능 우선순위
    ├── planner/       ← 화면 기획안, 기능 명세서, User Flow
    ├── designer/      ← 디자인 스펙, 컴포넌트 스펙
    ├── ux-writer/     ← 라이팅 가이드, 화면별 문구 시트
    ├── engineer/      ← 동작하는 프론트엔드 코드, 빌드 결과
    └── session.md     ← 작업 세션 체크포인트 (오케스트레이터 자동 관리)
```
