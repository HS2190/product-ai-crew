# PRD: 포트폴리오 사이트 → 개인 브랜딩 사이트 전환

> 서비스: ahn-brand (https://ahn-hyeonseo.vercel.app · repo HS2190/ahn · Astro · Vercel 자동 배포)
> 작성: PM · 2026-10-25 · v1.0
> 플랫폼: web (반응형 — 데스크톱 우선 + 모바일 대응)
> 선행 문서: 브랜드 정의서 `workspace/ahn-brand/pm/brand-definition.md` · 페르소나 `workspace/ahn-brand/persona.md`
> 이 PRD는 "무엇을 할 수 있어야 하는가"까지만 정한다. 화면 구성·컴포넌트·레이아웃·인터랙션은 기획자와 디자이너가 정한다.

## 0. 근거와 한계

- **리서치 단계 생략.** Researcher 산출물이 없다. 근거는 사용자 확정 사항 5개, 현재 사이트 원문, 오케스트레이터 진단 3개, 레퍼런스 25장·시안 7종에 대한 사용자 반응, 기억층이다(`context.md`).
- **방문자 데이터 없음.** 페르소나는 가설이며(persona.md 서두), 현재 사이트의 GA4 베이스라인(유입 경로·이탈·체류)을 아직 확인하지 않았다. 그래서 KPI 목표는 절대값이 아니라 **베이스라인 대비**로 두고, 베이스라인 확보를 첫 요구사항(FR-001)으로 둔다.
- **트래픽 규모가 작을 가능성.** 개인 사이트라 통계적으로 유의한 비교가 어렵다. 판정 규칙(2.4)에 최소 표본 조건과 정성 테스트 보조를 둔다.
- 우선순위 원칙(기억층): 사용자 확정 사항은 외부 지정 스펙에 준해 Must 고정, 우리가 선택한 추가 기능은 효과가 추정이면 Should로 강등하고 검증 조건을 단다. "기능이 있다"(Must 가능)와 "그 기능이 기억에 남게 한다"(가설)는 분리한다(default decisions 2026-06-30).

## 1. 배경 및 목적

### 1.1 문제

현재 사이트는 내용이 충실하지만 방문자가 **이력서를 읽고 나간다.** 사람이 기억에 남지 않는다. 원인은 세 가지다(오케스트레이터 진단, 관찰 등급).

| # | 문제 | 증상 | 영향받는 페르소나 |
|---|------|------|---------------|
| P1 | 정보가 이력서 순서다 | 히어로 → 케이스 6 → 일하는 방식 → 경력 → 연락. 사람보다 작업 목록이 먼저 보인다. 스타일을 바꾼 시안 7종도 같은 구성이라 "잘 정리된 이력서"로 읽힌다 | P1 한서윤, P2 정민호 |
| P2 | 관점이 보이지 않는다 | "From screens to systems"는 하는 일을 말하지만 무엇을 믿는지, 어떻게 다르게 보는지는 말하지 않는다 | P2 정민호 |
| P3 | 고유한 장치가 없다 | 시안 7종 모두 레퍼런스 스타일 차용. 얼굴 사진도 쓰지 않기로 해서 사람의 흔적이 더 약하다 | 전원 |
| P4 | "직접 만든" 증거가 흩어져 있다 | GitMate·Iris가 제품 케이스 사이에 섞여 있고, Product AI Crew는 "with AI 도구" 목록 한 줄이다. 포지셔닝의 핵심 증거가 묻혀 있다 | P2 정민호, P3 박도현 |

> P4는 PM 추가 진단이다(현재 사이트 구조 원문 기준, 관찰 등급).

### 1.2 목적

방문자가 이력서가 아니라 **"필요한 것이 없으면 직접 만드는 디자이너, 안현서"를 기억하고 나가게** 한다. 포지셔닝이 첫 화면부터 읽히고, 관점 3개가 작업 전체에서 반복 확인되며, 만든 것이 실제로 돌아가는 것을 확인할 수 있어야 한다.

포지셔닝 문장은 브랜드 정의서 추천안 B 기준이다. 사용자가 다른 안을 고르면 문구만 바뀌고 요구사항 구조는 그대로다.

## 2. 목표

### 2.1 비즈니스 목표
- 방문자가 "이 사람"을 한 문장으로 기억하게 한다 — 포지셔닝 "직접 만드는 디자이너"
- 채용·협업 대화가 시작되는 경로(연락)를 지금보다 더 많이 연다
- 이력서형 정보는 줄이지 않되 첫인상 자리에서 내린다 (P1 한서윤의 확인 니즈는 지킨다)

### 2.2 사용자 목표
| 페르소나 | 목표 |
|---------|------|
| P1 한서윤 (1분 스크리너) | 1분 안에 직무·연차·차별점 한 문장을 확인하고 PDF·연락처에 도달 |
| P2 정민호 (판단을 보는 사람) | 관점이 케이스에서 반복되는지, 만든 것이 돌아가는지, AI와 본인 판단의 경계를 확인 |
| P3 박도현 (만드는 동료) | 직접 만든 것과 동작 증거를 찾고, 가볍게 연락 |

### 2.3 성공 지표 (GA4)

전제: 본인 방문(`?me=1` internal 표시)은 모든 지표에서 제외한다. 이벤트 정의는 FR-012.

| ID | 지표 | GA4 정의 | 목표 | 연결 문제 | 등급 |
|----|------|---------|------|---------|------|
| K1 | 관점·이야기 도달률 | 관점 또는 이야기 영역이 노출된 세션 / 전체 세션 (`section_view` section_id ∈ {beliefs, story} 또는 해당 페이지 `page_view`) | 베이스라인 대비 상승 | P1·P2 | 가설 |
| K2 | 증거 확인률 | `proof_click`(link_type: demo·docs·repo·package)이 1회 이상인 세션 / 전체 세션 | 베이스라인 대비 상승 | P4 | 가설 |
| K3 | 연락 전환율 | `contact_click`(channel: email·linkedin·github) 또는 `email_copy`가 1회 이상인 세션 / 전체 세션 | 베이스라인 대비 상승 | 비즈니스 목표 | 가설 |
| K4 | 첫인상 통과율 | 홈 랜딩 세션 중 두 번째 이후 영역 `section_view` 또는 두 번째 `page_view`가 발생한 비율 | 베이스라인 대비 상승 | P1 | 가설 |
| K5 | 참여 시간 | 세션당 평균 참여 시간(GA4 기본 `user_engagement`), 케이스 상세 페이지별 평균 참여 시간 | 베이스라인 대비 하락 없음 | 전체 | 가설 |
| G1 | (가드레일) 케이스 열람률 | `case_open` 1회 이상 세션 / 전체 세션 | 베이스라인 대비 **하락하지 않음** | 이력서 정보를 내린 부작용 감시 | — |
| G2 | (가드레일) PDF 다운로드율 | `pdf_download` 세션 / 전체 세션 | 베이스라인 대비 하락하지 않음 | P1 니즈 보호 | — |

**보조 지표 (GA4 밖, 정성)** — "기억"은 GA4로 직접 잴 수 없으므로 보조로 둔다.
- 기억 테스트: 사이트를 처음 보는 3~5명에게 2분 탐색 후 "이 사람을 한 문장으로" 질문. 응답에 "만든다/직접" 계열 표현이 나온 비율. 목표 과반. 출시 전(시안) 1회, 출시 후 1회.

### 2.4 판정 규칙
- 비교 기간: 출시 전 4주 베이스라인 vs 출시 후 8주.
- 내부 트래픽 제외 후 기간당 **외부 세션 100 미만**이면 GA4 지표로 성공·실패를 판정하지 않고 방향 참고로만 쓴다. 이때는 보조 지표(기억 테스트)를 주 판정 근거로 삼는다.
- 유입 경로(referrer)별로 쪼개 본다. 지원서 발송 시기에 따라 유입 구성이 크게 바뀌므로, 전체 평균만으로 판정하지 않는다.

## 3. 타겟 사용자

`workspace/ahn-brand/persona.md` 참조 (가설 페르소나).

- **P1 한서윤 — 1분 스크리너** (리크루터/HR): 첫 화면에서 직무·차별점, 두 번 이내에 경력·PDF·연락처
- **P2 정민호 — 판단을 보는 사람** (디자인 리드/하이어링 매니저): 관점 → 케이스 반복 → 동작 증거 → AI 경계. 케이스 상세 딥링크로 들어오는 경우가 많다
- **P3 박도현 — 만드는 동료** (개발자/메이커): 저장소·문서에서 유입, 만든 것과 동작 증거, 가벼운 연락

### 유저 스토리
- **US-1** (P1·P2·P3) 처음 들어온 방문자로서, 작업 목록을 보기 전에 이 사람이 누구이고 무엇을 믿는지 알고 싶다 — 그래야 작업을 어떤 눈으로 볼지 정할 수 있다.
- **US-2** (P1) 채용 담당자로서, 직무·연차·최근 회사·PDF를 빠르게 확인하고 싶다 — 1차 매칭 판단을 해야 하므로.
- **US-3** (P2) 디자인 리드로서, 이 사람의 관점이 실제 케이스에서 반복되는지 확인하고 싶다 — 말뿐인 철학인지 가려야 하므로.
- **US-4** (P2·P3) 직접 만든 것을 보고 싶은 방문자로서, 왜 만들었는지와 실제로 돌아가는지를 확인하고 싶다.
- **US-5** (P2) AI를 쓰는 디자이너를 검토하는 사람으로서, AI가 한 일과 본인이 판단한 일의 경계를 알고 싶다.
- **US-6** (전원) 대화를 시작하고 싶은 방문자로서, 어느 페이지에서든 내 상황에 맞는 연락 경로를 찾고 싶다.
- **US-7** (P2) 케이스 상세로 바로 들어온 방문자로서, 홈을 거치지 않아도 이 사람이 누구인지 알고 다른 곳으로 이동하고 싶다.

## 4. 기능 범위

### 4.1 영역 후보 — "무엇을 할 수 있어야 하는가"

아래는 방문자가 할 수 있어야 하는 일의 묶음이다. **페이지 수·분리·병합·순서는 기획자가 정한다.** (예: Making을 별도 영역으로 둘지, 작업 영역 안의 다른 보기 방식으로 둘지는 기획 판단.)

| 영역 후보 | 방문자가 할 수 있어야 하는 것 | 주 페르소나 |
|----------|---------------------------|----------|
| 홈 (첫인상) | 이 사람이 누구인지(포지셔닝), 무엇을 믿는지(관점 최소 1개 이상의 단서), 사람의 흔적을 작업 목록보다 먼저 인지한다. 원하는 곳(작업·만든 것·이야기·연락)으로 바로 갈 수 있다 | 전원 |
| 작업 (Work) | 6개 케이스를 훑고, 각 케이스가 어떤 결핍을 다뤘고 어떤 관점과 연결되는지 알고, 상세로 들어간다 | P1·P2 |
| 만든 것 (Making/Lab) | 직접 만든 것(시스템·도구·에이전트 팀)을 "무엇이 없었나 → 무엇을 판단했나 → 돌아가는 증거" 순으로 확인하고, 증거(데모·문서·저장소)로 이동한다 | P2·P3 |
| 이야기·관점 (About) | 관점 3개를 읽고, 제조 현장부터 지금까지의 이야기를 따라가며, 각 관점이 어느 케이스에서 왔는지 이동한다. 경력 요약과 PDF에 도달한다 | P2·P1 |
| 연락 (Contact) | 이메일·LinkedIn·GitHub 중 자기 상황에 맞는 경로로 연락하고, 이메일 주소를 복사할 수 있다 | 전원 |

| F08 | 경력 요약·PDF 포트폴리오에 두 번 이내 이동으로 도달 | **Must** | High / Low | P1 핵심 니즈, 가드레일 G1·G2. 첫인상에서 내리되 접근성은 유지 |

| F10 | 딥링크 랜딩 대응: 케이스 상세에서 누구인지 + 다른 영역 이동 | **Must** | High / Low | P2 유입 패턴(US-7), 기존 PDF·이력서 속 링크 |
| F11 | 기존 URL 보존 (케이스 상세 등 기존 공개 주소가 깨지지 않음) | **Must** | High / Low | 이미 배포된 PDF·지원서·저장소 README의 링크가 이 사이트를 가리킴. 깨지면 P1·P2 유입이 바로 끊김 |
| F12 | 상태 표시: 상세 준비 중·런칭 전·업데이트 중을 범위를 한정해 표시 | **Should** | Medium / Low | 엣지케이스(5.3). 현재 전역 '업데이트 중' 알약은 사이트 전체가 미완성이라는 신호를 줌 — 가설이라 Should |
| F13 | 관점 ↔ 케이스 ↔ 만든 것의 상호 이동 (케이스에서 관련 관점·만든 것으로) | **Should** | Medium / Medium | 관점이 "반복된다"는 체감(US-3)을 높일 것이라는 가설. 검증: K1이 출시 후에도 베이스라인 수준이면 Must 승격 검토 |
| F14 | 공유 미리보기: 링크 공유 시 포지셔닝이 드러나는 제목·설명·이미지 | **Should** | Medium / Low | LinkedIn·메신저 공유가 유입의 일부라는 가설(P1→P2 전달 시나리오). 검증: GA4 referrer에서 LinkedIn·메신저 비중 확인 시 Must |
| F15 | "지금 만드는 것" — 현재 진행 중인 만들기를 짧게 보여줌 | **Nice to Have** | Medium / Low | "직접 만드는"의 현재성 신호. 단 갱신 안 되면 역효과(오래된 날짜) — 갱신 주기를 지킬 수 있을 때만 |
| F16 | 다크 모드 | **Nice to Have** | Low / Medium | 브랜드 목표와 무관 |

### 4.3 In Scope
F01–F16 중 Must 11개(F01–F11) 전부, Should 3개(F12–F14). Nice to Have(F15·F16)는 Must·Should 완료 후 여유 시.

## 5. 요구사항

### 5.1 기능 요구사항

**FR-001 측정 베이스라인** (F01)
- 리뉴얼 출시 전, 현재 사이트에 FR-012의 이벤트를 먼저 적용하고 4주간 베이스라인을 수집할 수 있어야 한다.
- 수용 기준: GA4에서 FR-012의 모든 이벤트가 내부 트래픽 제외 필터 적용 상태로 조회된다. 베이스라인 4주치 K1–K5·G1·G2 값이 기록된다.
- 예외: 현재 구조에 대응 영역이 없는 이벤트(예: Making 영역)는 베이스라인 0으로 기록하고, 해당 지표는 출시 후 절대값 추이로만 본다.

**FR-002 첫인상** (F02)
- 처음 들어온 방문자는 작업 목록보다 먼저 ① 이름 ② 직무(프로덕트 디자이너) ③ 포지셔닝 문장 ④ 사람의 흔적(F06)을 인지할 수 있어야 한다.
- 수용 기준: 데스크톱 1440×900, 모바일 390×844 첫 화면(스크롤 전)에 ①②③이 텍스트로 보인다. 첫 화면에서 가장 먼저 나오는 콘텐츠 묶음이 케이스 목록이 아니다.
- 수용 기준: 첫 화면에서 작업·만든 것·이야기·연락 각각으로 1회 조작으로 이동할 수 있다.

**FR-003 직무 확인** (F02·F08)
- 개인 브랜딩 표현이 직무를 가리지 않아야 한다. 은유적 문장만 있고 직무가 빠진 상태가 되면 안 된다.
- 수용 기준: 첫 화면에 "Product Designer"(또는 프로덕트 디자이너)와 경력 시작 연도(2020)가 텍스트로 있다.

**FR-004 관점 제시** (F03)
- 방문자는 관점 3개를 한곳에서 읽을 수 있어야 하고, 각 관점에서 근거가 된 케이스로 이동할 수 있어야 한다.
- 수용 기준: 관점 ①②③ 각각에 최소 1개 케이스로 이동하는 경로가 있다(①→Wepair·Gocha, ②→Dr's Solution·Sensicon, ③→Iris·GitMate·Product AI Crew; 브랜드 정의서 2절 매핑).
- 수용 기준: 관점 문장은 사이트 전체에서 동일한 표현으로 쓰인다(영역마다 다른 슬로건 금지).

**FR-005 관점의 반복 확인** (F04·F13)
- 각 케이스는 연결된 관점이 무엇인지 방문자가 알 수 있어야 한다.
- 수용 기준: 6개 케이스 각각에 연결 관점(①②③ 중 1개 이상)이 표시된다.

**FR-006 사람의 존재감** (F06)
- 얼굴 사진 없이, 본인 손에서 나온 흔적(손글씨·드로잉)이 사이트 전체에 걸쳐 콘텐츠와 결합된 형태로 존재해야 한다. 장식용 단독 배치가 아니라 "판단(왜)"을 전달하는 역할이어야 한다(브랜드 정의서 6절).
- 수용 기준: 첫 화면과 최소 3개 케이스에 손의 흔적이 콘텐츠(판단 메모 등)와 결합되어 있다. 얼굴 사진이 사이트 어디에도 없다.
- 수용 기준: 손글씨로 전달되는 모든 정보는 동일 내용의 텍스트로도 제공된다(스크린 리더로 읽힘). 포지셔닝·관점·연락처는 손글씨로만 전달되지 않는다.
- 의존: 손글씨·드로잉 원본 제공 가능 여부 `[확인 필요]`. 불가 시 대안은 디자이너가 제안하되, 손글씨 폰트로의 대체는 장치 의미가 약해지므로 사용자 승인 필요.

**FR-007 만든 것** (F05)
- 방문자는 직접 만든 것들을 하나의 묶음으로 볼 수 있어야 하며, 각 항목에서 ① 무엇이 없었나 ② 무엇을 판단했나(버린 것 포함) ③ 돌아가는 증거를 확인할 수 있어야 한다.
- 대상(최소): Iris, GitMate, Product AI Crew. user-voice-sim은 증거 링크 확보 시 포함 `[확인 필요]`.
- 수용 기준: 각 항목에 ①②③이 모두 있다. ③은 최소 1개의 외부 링크(데모·문서·저장소·패키지) 또는 FR-011의 대체 자료다. ③이 없는 항목은 노출하지 않는다("돌아가야 설계다").
- 수용 기준: Product AI Crew 항목은 AI가 맡는 일과 본인이 판단·검수하는 지점의 경계를 명시한다(US-5).
- 제약: GitMate·Iris는 케이스(F04)에도 있다. 같은 콘텐츠를 두 번 다른 내용으로 관리하지 않도록, 두 영역이 같은 원본을 가리키게 하는 방식은 기획자가 정한다.

**FR-008 경력·PDF 도달** (F08)
- 방문자는 어느 영역에서든 두 번 이내 조작으로 경력 요약과 PDF 포트폴리오에 도달할 수 있어야 한다.
- 수용 기준: 경력 요약에 현 재직(티엘씨헬스케어)·이전 회사·기간·역할이 현재 사이트와 같은 사실로 있다. 제조·웹 디자인 이전 경력도 포함한다.
- 수용 기준: PDF 링크는 새 탭으로 열리며, 클릭 시 `pdf_download`가 기록된다.

**FR-009 연락** (F09)
- 방문자는 어느 영역에서든 연락 경로(이메일·LinkedIn·GitHub)에 도달할 수 있어야 하고, 이메일 주소를 클릭 한 번으로 복사할 수 있어야 한다.
- 수용 기준: 모든 페이지에서 연락 경로까지 1회 조작. 이메일은 mailto 링크와 텍스트 복사가 모두 가능하며 복사 성공이 사용자에게 알려진다.
- `[확인 필요]` GitHub 프로필을 연락 채널로 공개할지.

**FR-010 딥링크 랜딩** (F10)
- 케이스 상세나 만든 것 상세로 바로 들어온 방문자도 이 사람이 누구인지(이름·포지셔닝) 알 수 있고, 홈·관점·연락으로 이동할 수 있어야 한다.
- 수용 기준: 모든 상세 페이지에 이름과 포지셔닝(또는 그 축약)이 있고, 홈·이야기·연락으로 1회 조작 이동이 가능하다.

**FR-011 기존 URL 보존** (F11)
- 리뉴얼 후에도 현재 공개된 모든 URL로 들어온 방문자가 해당 콘텐츠(또는 가장 가까운 콘텐츠)에 도달해야 한다.
- 수용 기준: 리뉴얼 전 사이트맵의 모든 URL이 200 또는 301(대응 페이지)로 응답한다. 404가 0건이다.

**FR-012 이벤트 계측** (F01)
- 아래 이벤트가 GA4에 기록되어야 한다. 이벤트명·파라미터는 Engineer가 조정 가능하나 지표 정의(2.3)가 계산 가능해야 한다.

| 이벤트 | 파라미터 | 시점 |
|-------|---------|------|
| `section_view` | section_id, page | 주요 영역이 화면에 50% 이상 들어왔을 때, 페이지당 영역별 1회 |
| `case_open` | case_id, source(home·work·beliefs·making·direct) | 케이스 상세 진입 |
| `making_open` | item_id, source | 만든 것 상세 진입(상세가 있을 경우) |
| `proof_click` | item_id, link_type(demo·docs·repo·package·fallback) | 증거 링크 클릭 |
| `contact_click` | channel(email·linkedin·github), page | 연락 경로 클릭 |
| `email_copy` | page | 이메일 복사 |
| `pdf_download` | page | PDF 포트폴리오 클릭 |
| `case_unavailable_view` | case_id | 상세 준비 중 상태 노출(5.3) |

- 수용 기준: `?me=1` 내부 표시가 세션 내 페이지 이동 후에도 유지되어 내부 방문이 모든 이벤트에서 제외된다.

**FR-013 상태 표시** (F12)
- 미완성 상태는 해당 범위에서만 표시되어야 하며, 사이트 전체를 미완성으로 보이게 하면 안 된다. 5.3 엣지케이스 표의 각 상태를 따른다.
- 수용 기준: 전역 "업데이트 중" 표시가 없다. 상태가 있는 항목에는 상태와 마지막 갱신일(YYYY.MM)이 함께 있다.

**FR-014 상호 이동** (F13)
- 케이스에서 연결된 관점과 관련된 만든 것으로, 만든 것에서 그것이 쓰인 케이스로 이동할 수 있어야 한다.
- 수용 기준: 연결 관계가 있는 모든 쌍에 양방향 경로가 있다.

**FR-015 공유 미리보기** (F14)
- 사이트 링크를 메신저·LinkedIn에 붙였을 때 이름·포지셔닝이 미리보기에 나와야 한다. 케이스 상세 링크는 해당 케이스 한 줄이 나와야 한다.
- 수용 기준: 모든 페이지에 고유한 제목·설명·공유 이미지가 있다. LinkedIn Post Inspector에서 미리보기가 정상 표시된다.

### 5.2 비기능 요구사항

- **NFR-001 성능**: 모바일 Lighthouse(기본 모바일 프리셋) Performance 85 이상, LCP 2.5초 이하, CLS 0.1 이하. 손글씨·드로잉·일러스트 이미지는 첫 화면 외에는 지연 로드.
- **NFR-002 접근성**: WCAG 2.1 AA. 본문 대비 4.5:1, 큰 텍스트 3:1. 모든 이동·복사 기능이 키보드로 가능하고 포커스가 보인다. 이미지 대체 텍스트 100%. axe 자동 검사 위반 0건(critical·serious).
- **NFR-003 모션**: `prefers-reduced-motion` 설정 시 정보 전달에 필요한 것 외 움직임을 끈다. 콘텐츠가 모션 완료에 의존해 보이지 않는 상태가 없어야 한다(이전 myhome 리뉴얼에서 스크롤 트리거 숨김 상태가 데드락돼 이미지가 전부 안 보인 결함 이력).
- **NFR-004 반응형**: 320px부터 1920px까지 가로 스크롤 없이 렌더. 터치 대상 44×44px 이상. 호버로만 드러나는 정보가 없다.
- **NFR-005 JS 비의존 가독성**: JavaScript가 꺼져도 모든 텍스트 콘텐츠와 링크가 읽히고 동작한다(이메일 복사 등 보조 기능은 예외).
- **NFR-006 스택 유지**: Astro, Vercel 자동 배포, 기존 GA4 속성 유지.
- **NFR-007 콘텐츠 정확성**: 수치는 이전 확정 정본(4,027 · −63% · 5h→2h · 15→8 · 12회 · ~6.5초 · 1,393만)과 근거 등급을 벗어나지 않는다. 재직 중 회사 관련 정보는 공개 가능 범위만(5.3).
- **NFR-008 아이덴티티 분리**: 범용 PDF 덱의 색 조합(#F2EFE9 + #D2521E)과 도면 문법을 재사용하지 않는다(사용자 확정 2). 디자인 리뷰 체크 항목으로 둔다.
