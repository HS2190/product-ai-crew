## 1. 배경 및 목적

### 1.1 현재 구조의 문제

위페어 파트너스는 현재 차량 단위 폴더에 사진을 시간순으로 누적 저장하는 구조를 사용한다.

```
차량 폴더 (입고일_차량번호_차종)
└ 사진 (촬영 순서대로 누적)
```

4개 업체(투투자동차정비, 연일자동차공업사, 기아오토큐 중부산서비스, 기아오토큐 함안서비스) 공통 피드백 분석 결과, 이 구조는 다음 두 가지 문제를 야기한다.

**문제 1 — 공정 맥락 없는 사진 혼재**
판금/도장 등 복수 공정이 동시 진행되는 현장에서 수백 장의 사진이 시간순으로 섞인다. 어느 사진이 어느 공정에 속하는지 사후에 식별하려면 사진 내용을 일일이 육안 확인해야 한다.

**문제 2 — 행정 비효율과 보험 청구 리스크**
관리자(박정훈, 50세)는 매일 1~2시간을 사진 분류·폴더링에 소비한다. 보험사 제출 시에는 공정별 증빙 사진을 따로 설명하거나 재편집해야 하며, 출고 직전 사진 누락이 발견되면 보험 청구 자체가 불가능해지는 재무 리스크가 발생한다.

### 1.2 해결 방향

업체 단위 옵션 토글로 "공정별 하위 폴더 자동 생성·라우팅" 기능을 제공한다. 옵션을 활성화한 업체는 아래 구조로 전환된다.

```
차량 폴더 (입고일_차량번호_차종)
└ 공정별 폴더
  ├ 초기
  ├ 판금
  ├ 도장
  ├ 완성
  ├ 하체
  └ 서류
```

공정 병행이 거의 없는 업체는 기존 단일 폴더 구조를 유지할 수 있어 강제 전환으로 인한 혼란을 방지한다.

## 3. 타겟 사용자

### 3.1 주요 페르소나

#### 박정훈 (관리자) — 50세 / 공업사 대표

- **환경**: 사무실 PC + 안드로이드 폰 멀티태스킹. 착석, 깨끗한 손, WiFi
- **디지털 숙련도**: 중간
- **핵심 Pain Point**: 매일 1~2시간 사진 분류 야근 / 보험 청구 번거로움
- **이 기능에서의 역할**: 업체 단위 공정 분류 옵션 ON/OFF 결정, 공정 셋 커스터마이징

#### 최성호 (작업자) — 55세 / 공업사 부장

- **환경**: 현장 이동 중, 장갑 착용, 기름때, 소음 심함, 네트워크 불안정
- **디지털 숙련도**: 낮음 (큰 버튼 위주, 글 읽지 않음, 복잡하면 즉시 포기)
- **핵심 Pain Point**: 조작 번거로움 / 추가 정리 행동 요구 시 앱 이탈
- **이 기능에서의 역할**: 촬영 시 현재 공정 선택, 사진 촬영 연속 수행

### 3.2 사용 시나리오

**시나리오 A — 관리자 초기 설정**
박정훈이 앱 > 설정 > 공정별 분류에서 토글을 ON한다. 기본 6개 공정(초기/판금/도장/완성/하체/서류)이 보인다. "하체" 공정을 거의 쓰지 않아 숨김 처리한다. 설정 완료 후 신규 입고 차량부터 공정 폴더 구조가 적용됨을 확인한다.

**시나리오 B — 작업자 촬영 중 공정 선택**
최성호가 판금 작업 중 갤러리 > FAB 버튼으로 카메라를 연다. 화면 상단에 현재 공정 칩 "판금"이 표시되어 있다(직전 선택 유지). 변경 없이 연속 촬영한다. 도장 부스로 이동 후 공정 칩을 탭하여 "도장"으로 변경 후 계속 촬영한다.

**시나리오 C — 관리자 보험사 제출**
박정훈이 PC에서 구글 드라이브를 열면 해당 차량 폴더 안에 공정별 하위 폴더가 이미 생성되어 있다. "판금" 폴더에서 AOS에 필요한 사진을 드래그 앤 드롭으로 삽입한다. 추가 설명이나 재분류 없이 청구를 완료한다.

## 5. 요구사항

### 5.1 기능 요구사항

#### F-1: 업체 단위 공정별 분류 옵션 토글

- FR-1-01: 관리자 권한 사용자는 앱 내 설정 화면에서 "공정별 분류" 토글을 ON/OFF할 수 있어야 한다
- FR-1-02: 토글 상태는 업체(공업사) 단위로 저장되어 해당 업체의 모든 작업자에게 동일하게 적용된다
- FR-1-03: 토글 전환 시 적용 시점(신규 입고 차량부터)을 안내하는 확인 다이얼로그가 노출된다
- FR-1-04: ON 상태에서 OFF로 전환해도 기존 공정 분류된 차량의 폴더 구조는 변경되지 않는다

#### F-2: 공정 셋 관리

- FR-2-01: 위페어 기본 공정 셋 6개(초기 / 판금 / 도장 / 완성 / 하체 / 서류)가 기본값으로 제공된다
- FR-2-02: 관리자는 공정 이름을 변경할 수 있다 (최대 8자)
- FR-2-03: 관리자는 기본 공정을 "숨김" 처리할 수 있다. 숨긴 공정은 작업자 화면에 노출되지 않는다. 단, 삭제는 불가하며 언제든 다시 표시로 복원할 수 있다
- FR-2-04: 관리자는 커스텀 공정을 추가할 수 있다 (최대 10개, 기본 6개 포함)
- FR-2-05: 공정 순서를 드래그로 재정렬할 수 있다
- FR-2-06: 보험사 매핑 표준(초기/판금/도장/완성/하체/서류)은 기본 셋 기준을 유지한다. 커스텀 공정은 "기타" 카테고리로 자동 매핑된다

#### F-3: 카메라/갤러리 진입 시 현재 공정 칩 노출 (Sticky 모드)

- FR-3-01: 공정별 분류 옵션이 ON인 업체의 작업자가 카메라 또는 갤러리 화면에 진입하면 화면 상단에 현재 공정 칩이 항상 노출된다
- FR-3-02: 최초 진입 시 관리자가 작업자 배정 시 지정한 공정이 기본값으로 표시된다. 배정 공정이 없을 경우 첫 번째 공정이 기본값이 된다
- FR-3-03: 한 번 선택된 공정은 작업자가 직접 변경하기 전까지 유지된다 (앱 재시작 시 초기화)
- FR-3-04: 공정 칩은 터치 영역이 충분히 커야 하며(최소 44dp), 장갑 착용 상태에서도 오조작 없이 탭 가능하도록 설계한다

#### F-4: 공정 변경 시트

- FR-4-01: 작업자가 공정 칩을 탭하면 하단에서 올라오는 바텀 시트(Bottom Sheet)로 공정 목록이 표시된다
- FR-4-02: 각 공정 버튼은 한 손 조작이 가능하도록 세로 리스트 형식으로 배치되며 버튼 높이는 최소 56dp 이상으로 설정한다
- FR-4-03: 현재 선택된 공정은 선택 상태(체크 또는 하이라이트)로 구분 표시된다
- FR-4-04: 공정 선택 즉시 바텀 시트가 닫히고 칩이 업데이트되며 촬영 화면으로 복귀한다

#### F-5: 사진 메타에 공정 값 저장

- FR-5-01: 촬영 또는 갤러리에서 추가된 사진에는 현재 선택된 공정 값이 메타데이터로 함께 저장된다
- FR-5-02: 공정 값은 사진 파일의 커스텀 메타 필드 또는 별도 DB 레코드로 관리한다 (EXIF 외부 저장 방식 허용)
- FR-5-03: 네트워크 오프라인 상태에서도 로컬에 공정 메타가 저장되며, 업로드 시 함께 전송된다

#### F-6: 구글 드라이브 공정별 하위 폴더 자동 생성·라우팅

- FR-6-01: 공정별 분류 옵션이 ON인 차량의 사진 업로드 시, 구글 드라이브의 차량 폴더 아래에 공정명 하위 폴더가 자동 생성된다
- FR-6-02: 사진은 공정 메타 값에 따라 해당 하위 폴더에 저장된다
- FR-6-03: 공정 메타가 없는 사진은 "미분류" 폴더로 라우팅된다
- FR-6-04: 폴더 생성은 최초 해당 공정 사진 업로드 시 자동으로 생성된다 (빈 폴더 사전 생성 불필요)

#### F-7: 옵션 토글 전환 시점 정책

- FR-7-01: 옵션 ON 전환 후에는 신규 입고 등록된 차량부터 공정별 폴더 구조가 적용된다
- FR-7-02: 옵션 ON 전환 시점에 이미 진행 중인 차량 및 기존 차량은 기존 단일 폴더 구조를 그대로 유지한다
- FR-7-03: 관리자는 어느 차량이 새 구조 적용 대상인지 차량 목록에서 시각적으로 구분할 수 있어야 한다 (예: 공정 아이콘 표시)

#### F-8: 공정 확인 토스트 [Should Have]

- FR-8-01: 동일 공정으로 30분 이상 연속 촬영하거나 50장 이상 누적 시, "현재 공정: [공정명]. 계속 진행하시겠어요?" 토스트가 노출된다
- FR-8-02: 토스트는 화면 하단 중앙에 위치하며 5초 후 자동 소멸한다
- FR-8-03: 작업자가 토스트에서 "공정 변경"을 탭하면 공정 변경 시트가 열린다

### 5.2 비기능 요구사항

## 6. 공정 선택 UX 방안 비교

> **의사결정 필요**: 디자인 착수 전 비즈니스팀 확인 후 방안 확정 필요

### 6.1 비교 대상

| | 방안 1 | 방안 2 |
|--|--------|--------|
| **명칭** | 관리자 배정 + Sticky 칩 + 진입 확인 토스트 | 개발팀 제안 — 상단 드롭다운 (매번 선택) |
| **제안 출처** | 기획 | 개발팀 |

### 6.2 방안 1 — 관리자 배정 + Sticky 칩 + 진입 확인 토스트

**개요**

관리자가 작업 배정 시 담당 공정을 미리 지정하고, 작업자 카메라 진입 시 "현재 공정: 판금" 확인 토스트를 2초간 표시 후 자동 소멸. 공정이 바뀔 때만 작업자가 칩을 탭해 변경.

**사용자 플로우**

관리자(박정훈):
```
차량 입고 등록 → 작업자 배정 화면
  → 작업자 선택 + 담당 공정 지정 (드롭다운: 판금)  ← 신규 추가 단계
  → 저장
```

작업자(최성호):
```
차량 선택 → 사진 등록 탭 → 카메라 열기
  → 진입 토스트 표시 (2초 자동 소멸)
    ● 현재 공정: 판금  [변경]
  → (추가 탭 불필요) 바로 촬영 → 판금 폴더에 자동 저장
  → 공정 변경 시: 칩 탭 → 바텀 시트 → 공정 선택
```

**장점**
- 작업자 추가 탭 수: **0회** (공정 변경 없을 때)
- 장갑 착용·소음 현장에서도 그냥 찍기만 하면 됨
- 오분류 위험 낮음: 관리자 사전 배정 + 진입 토스트 2차 확인
- 배정 화면에서 누가 어떤 공정 담당인지 한눈에 파악 가능
- 추후 공정 현황 대시보드(F-9)로 자연스럽게 연결 가능

**단점 및 리스크**

| 리스크 | 완화 방법 |
|--------|---------|
| 관리자가 공정 배정을 빠뜨리는 경우 | 배정 없으면 칩 = "공정 선택" → 작업자가 1회 직접 선택 (fallback 자동 적용) |
| 작업자가 공정 변경 후 관리자가 모르는 경우 | 토스트에 변경 이력 기록 가능 (2차 스프린트) |
| 오프라인 환경 | 앱 실행 시 배정 데이터 로컬 캐싱 (개발팀 확인 필요) |

**개발 범위 (추가 필요)**
- 관리자 화면: 작업자 배정 시 "담당 공정" 필드 추가 (기존 화면에 드롭다운 1개 추가)
- 서버: 작업 배정 테이블에 `process_id` 필드 추가
- 작업자 앱: 카메라 진입 시 배정 공정 조회 + 진입 토스트 표시 + Sticky 유지

### 6.3 방안 2 — 상단 드롭다운 (매번 선택)

**개요**

카메라 화면 상단에 공정 선택 드롭다운을 배치. 작업자가 카메라를 열 때마다 드롭다운에서 공정을 선택한 뒤 촬영.

**사용자 플로우**

관리자(박정훈):
```
차량 입고 등록 → 작업자 배정
공정 배정 없음 — 작업자가 직접 매번 선택
```

작업자(최성호):
```
차량 선택 → 사진 등록 탭 → 카메라 열기
  → 상단 드롭다운에서 공정 선택  ← 매번 필수
    [ 원본화질   공정 선택 ▾ 판금   ⚡ ]
  → 촬영 → 선택한 공정 폴더에 저장
  → 다른 공정 찍으려면 → 드롭다운 다시 선택
```

**장점**
- 구현 단순: 기존 화면에 드롭다운 1개 추가, 서버 배정 구조 변경 불필요
- 매번 명시적 선택 → 오분류 원천 차단
- 관리자 화면 변경 없음

**단점 및 리스크**

| 문제 | 심각도 |
|------|--------|
| 카메라 열 때마다 드롭다운 필수 조작 → 같은 공정 20장 촬영 시 20번 확인 | 높음 |
| 상단 UI는 한 손 파지 시 엄지 데드존 — 장갑 착용 환경에서 조작 어려움 | 높음 |
| 드롭다운 펼쳐질 때 뷰파인더 일부 가림 | 중간 |
| 기존 상단 바(원본화질·플래시)와 공간 충돌 | 중간 |
| "귀찮다" → 사진 등록 기피로 이어질 위험 (최성호 페르소나 핵심 리스크) | 매우 높음 |

### 6.4 비교 요약

| 항목 | 방안 1 (관리자 배정 + Sticky) | 방안 2 (드롭다운 매번 선택) |
|------|------------------------------|--------------------------|
| **작업자 추가 탭 수** | **0회** (공정 변경 없을 때) | **매번 1회 이상** |
| **오분류 위험** | 낮음 (배정 + 토스트 2중 확인) | 매우 낮음 (강제 선택) |
| **장갑 환경 대응** | ✅ 최적 | ❌ 상단 드롭다운 조작 어려움 |
| **사진 등록 기피 위험** | 낮음 | **높음** |
| **관리자 추가 작업** | 배정 시 공정 지정 (1회/차량) | 없음 |
| **개발 공수** | 중간 (배정 필드 + 캐싱) | 낮음 |
| **데이터 활용 가치** | 높음 (공정별 배정 이력 → 대시보드 연결) | 낮음 |
| **최성호 페르소나 부합** | ✅ | ❌ |
| **박정훈 페르소나 부합** | ✅ (사전 파악 가능) | △ |

### 6.5 비즈니스팀 확인 필요 사항

방안 결정 전 아래 운영 방식을 확인해 주세요.

**Q1. 작업자-공정 배정 방식**
> 현재 현장에서 작업자가 차량별로 담당 공정이 정해져 있나요, 아니면 그때그때 유동적으로 결정되나요?

- **정해져 있다** → 방안 1이 자연스러운 확장. 관리자가 입고 시 배정하면 됨
- **유동적이다** → 방안 1은 배정 누락 가능성 있음. fallback(직접 선택) 병행 운영으로 대응 가능

**Q2. 관리자의 배정 공수 수용 여부**
> 관리자(박정훈)가 차량 배정 시 공정 필드를 1개 더 입력하는 것이 괜찮은가요?

- **괜찮다** → 방안 1 진행 가능
- **부담이다** → 방안 1은 fallback(공정 배정 없으면 작업자 직접 선택)으로만 운영

**Q3. 오분류 허용 수준**
> 작업자가 실수로 잘못된 공정에 사진이 저장됐을 때 어느 수준까지 허용 가능한가요?

- 보험 청구·외부 제출 빈도가 높을수록 오분류 비용이 큼 → 방안 1 권장
- 내부 관리 목적만이라면 방안 2도 수용 가능

### 6.6 권장안

**방안 1 (관리자 배정 + Sticky + 진입 토스트)** 권장.

관리자가 배정을 빠뜨리는 경우를 대비한 fallback(작업자 직접 선택)을 함께 개발하면, 두 방안의 단점을 모두 커버하면서 최성호 페르소나의 핵심 제약(추가 탭 최소화)을 충족할 수 있습니다.

드롭다운(방안 2)은 "구현이 쉽다"는 장점이 있으나, 작업자의 사진 등록 기피로 이어질 경우 기능 자체가 현장에서 외면받을 위험이 있습니다.

## 8. 미결 사항 및 PM 결정

### O1: 다중 공정 사진(판금+도장 경계) 처리

**PM 결정**: **단일 태깅 (현재 선택된 공정으로만 저장)**

- 복수 태깅은 작업자에게 추가 선택 행동을 요구하여 최성호 페르소나 이탈 유발
- 사본 저장은 드라이브 용량 증가 및 AOS 제출 시 중복 문제 발생
- 추후 복수 태깅 수요가 실제 데이터로 확인되면 F-10과 함께 후속 검토

### O2: 공정 미선택(스킵) 허용 여부

**PM 결정**: **스킵 허용 + "미분류" 폴더로 라우팅**

- 강제 선택은 긴급 촬영 상황(소음, 이동 중)에서 앱 이탈을 유발
- 미분류 비율을 KPI로 관리. 20% 이상 지속 시 강제 선택 정책 전환 재검토
- 초기 진입 시 기본 공정이 Sticky로 자동 선택되므로 실질적 스킵은 드물 것으로 예상

### O3: 옵션 ON/OFF 권한 단위

**PM 결정**: **관리자 역할 전체 허용**

- 복수 관리자 업체에서 대표 부재 시 설정 변경 불가 문제 방지
- [확인 필요: 개발팀 권한 모델 현황 확인]

### O4: "초기·완성·서류" 공정 명칭 정의

**PM 결정**: **[확인 필요] — 현장 검증 후 확정**

- **권장 액션**: 기획 단계 진입 전 2~3개 업체 현장 인터뷰를 통해 6개 공정 명칭 현장 검증 필요

### O5: 보험사 제출 시 공정 매핑 표준

**PM 결정**: **기본 6개 셋 = 표준 매핑 고정. 커스텀 공정 = "기타" 자동 매핑**

- [확인 필요: AOS 연동 표준 코드 목록 개발팀 확인 후 기본 셋 명칭 최종 검토]

### O6: 자동 추정 신호 정의 (B안 진입 시 사전 검토)

**PM 결정**: **현 시점 정의 보류. Future 백로그로 관리**

- B안(자동 추정)은 MVP Out of Scope 확정
- A안 Sticky 모드 실사용 데이터 3개월 이상 축적 후 설계

## 10. 브랜드 방향성 및 톤앤매너

> 기획자·디자이너·UX 라이터에 전달하는 가이드라인

**핵심 가치**: "현장의 언어로, 최소한의 조작으로, 관리자가 바로 쓸 수 있게."

### 디자인 원칙

1. **현장 최적화 우선**: 소음·조명·장갑 환경을 전제로 한 UI. 글보다 아이콘과 색상으로 상태 전달
2. **신뢰 가능한 자동화**: 작업자가 찍기만 해도 정리가 된다는 신뢰를 UX로 구현. 불필요한 확인 요청 최소화
3. **관리자 흐름 중단 없음**: 설정 변경이 현장 흐름을 끊지 않도록 설계. 상태 변경은 즉시 반영

### 작업자 UX 톤

- 큰 버튼, 명확한 현재 상태 표시
- 행동 유도 문구는 1줄, 동사형 ("판금으로 촬영 중")
- 오류 메시지 없이 시스템이 자동 처리 (미분류 → 백그라운드 라우팅)

### 관리자 UX 톤

- 설정 화면은 행정 용어 친숙 (토글, 추가, 숨기기)
- 변경 영향 범위를 명확히 안내 ("다음 입고 차량부터 적용")
- 전문적이되 간결한 레이블. 불필요한 설명 텍스트 배제
