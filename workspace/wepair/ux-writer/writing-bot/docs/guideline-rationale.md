## Q1. 어떤 레퍼런스를 참고했어?

> **먼저 짚고 넘어갈 것:** `ux_writing_guideline.md`는 출처를 명시적으로 표기하지 않았습니다.
> 아래 표는 각 원칙의 내용을 분석해 **어떤 기준에서 나왔는지 역추적한 결과**입니다.
> 원칙이 여러 기준에 걸쳐 있는 경우 주요 기준만 표기했습니다.

| 원칙 | 참고 기준 | 근거 |
|------|---------|------|
| 브랜드 보이스 4원칙 (Clear / Warm but composed / Concise / Active) | 일반 UX Writing 방법론 (Nielsen Norman Group, Google Material Design Writing) | 네 가지 속성 구조는 업계 표준적인 Voice & Tone 프레임워크와 일치. 특히 "능동적으로(Active)"는 수동태 금지 원칙으로, NNG의 UX Writing 가이드와 동일한 방향 |
| 해요체 통일 (-해요 / -예요) | 국내 주요 서비스 UX Writing 관행 (카카오, 토스, 당근 등) + 서비스 사용자 분석 | B2B이지만 과도한 격식 회피. "공업사 현장 담당자"라는 사용자 특성 반영. 해요체는 국내 서비스에서 가장 보편적으로 채택된 비격식 존댓말 |
| 명사+명사 띄어쓰기 | 한글 맞춤법 (국립국어원) | 한글 맞춤법 제2장 제2절 띄어쓰기 기준. "합성어가 아닌 명사 나열은 띄어 쓴다"는 원칙에서 직접 도출 |
| "중(中)" 앞 띄어쓰기 | 한글 맞춤법 (국립국어원) | "중"은 의존 명사이므로 앞말과 띄어 씀. 표준국어대사전 표제어 기준 |
| "해 주세요" 띄어쓰기 | 한글 맞춤법 제47항 | 보조 용언 "주다"는 본용언과 띄어 씀 (허용 규정 있으나 UI 문구에서는 분리 표기가 명확성 측면에서 권장) |
| 조사 앞 띄어쓰기 ("아이디 입니다" 금지) | 한글 맞춤법 | "이다"는 서술격 조사로 앞 체언에 붙여 씀. "아이디예요"가 표준 |
| 번역투 제거 (~의 경우, ~을 통해, 본 서비스 등) | 국립국어원 번역 투 지침 + 국내 UX Writing 관행 | 일본어·영어 직역 표현 목록은 국립국어원 "번역 투 바로 쓰기" 자료와 내용 일치. 실제 전수조사에서 D 유형으로 분류된 항목들 |
| 높임말 과용 금지 ("보내드린" → "보낸") | 국립국어원 공공 언어 사용 지침 + 내부 원칙 | 시스템 주체와 사용자 주체를 구분하는 원칙. "드리다"는 사람 간 관계에서만 적절 |
| 에러 메시지: 원인 + 해결 방법 구조 | Nielsen Norman Group (Error Message Guidelines) | "Good error messages tell users what went wrong and how to fix it" — NNG의 10 Usability Heuristics #9와 동일한 방향 |
| 빈상태: 왜 비었는지 + 무엇을 하면 되는지 | Nielsen Norman Group (Empty State Design) + 내부 전수조사 패턴 | NNG Empty State 가이드: "empty states should explain why the area is empty and what the user can do" |
| 버튼: 동사형, 이동 버튼에 "~으로" 포함 | Apple Human Interface Guidelines + Google Material Design Writing | 두 가이드 모두 버튼 레이블은 동사형(Action labels)을 권장. 방향 포함은 국내 서비스 관행 기반 |
| 플레이스홀더: 형식·예시 표기 필수 | WCAG 2.1 접근성 가이드라인 (SC 3.3.2) + Nielsen Norman Group | "Inputs have example text" 원칙. 레이블과 중복 금지는 접근성과 인지 부하 관점에서 도출 |
| 용어 사전 (표준 표기 단일화) | 내부 전수조사 결과 | 화면 간 표기 불일치(A 유형)로 분류된 케이스들을 기반으로 작성. 외부 레퍼런스가 아닌 실제 앱 데이터 기반 |
| 검토 체크리스트 | 내부 전수조사 오류 패턴 종합 | 전수조사 116건 중 가장 빈번한 오류 순서로 항목 배치 (붙여쓰기 51.4% → 어투 불일치 20.0% 순) |

## Q2. 왜 이렇게 작성했어?

파일 내 원칙 순서대로 설명합니다.

---

### 1-3. 브랜드 보이스 & 톤 4원칙

**왜 4가지를 골랐는가?**

위페어 파트너스의 사용자는 공업사 현장 담당자입니다. 디지털 리터러시가 높지 않을 수 있고, 작업 현장에서 짧은 시간에 앱을 조작해야 합니다. 이 맥락에서 4가지 원칙이 도출됩니다.

- **명확하게(Clear):** 현장에서 헤맬 시간이 없다. 다음 행동이 즉시 보여야 한다.
- **친근하게(Warm but composed):** B2B 툴이지만 딱딱한 공문서 언어는 작업자에게 낯설다. 그렇다고 너무 캐주얼하면 신뢰감이 떨어진다.
- **간결하게(Concise):** 모바일 화면에서 긴 문장은 읽히지 않는다. 한 번에 한 메시지만 전달해야 오해가 없다.
- **능동적으로(Active):** 수동태(`~되었습니다`)는 주체가 누군지 모호하고 사용자가 무엇을 해야 하는지 보이지 않는다.

---

### 2-1. 해요체 사용 원칙

전수조사에서 어투 불일치가 20.0%(2위 오류)였습니다. `-합니다`, `-해요`, `-하십시오`가 화면마다 뒤섞여 있었습니다. 서비스 전체의 신뢰감은 일관성에서 나오기 때문에 단일 어미를 지정하는 것이 필요했습니다.

`-해요` 체를 선택한 이유는 두 가지입니다.
1. 비격식 존댓말이므로 B2B 툴에서도 어색하지 않다.
2. 국내 주요 서비스(토스, 카카오, 당근)가 이미 이 체계를 채택해 사용자 기대치와 일치한다.

법적 문서에 예외를 둔 것은 약관 본문에 해요체를 쓰면 법적 효력 해석에 혼선이 생길 수 있기 때문입니다.

---

### 2-2. 맞춤법·띄어쓰기 4가지 규칙

전수조사 오류의 51.4%가 붙여쓰기·맞춤법이었습니다. 가이드라인이 모든 맞춤법을 다룰 수는 없으므로, **실제 오류에서 반복적으로 발생한 패턴 4가지만** 선별했습니다.

- **규칙 1(명사+명사):** 피그마 레이어명이 그대로 레이블이 되는 경우가 많아 발생. 레이어명은 보통 붙여 씁니다(`작업완료`).
- **규칙 2("중" 띄어쓰기):** 상태 표시 UI에서 자주 등장하고(`처리중`, `작업중`), 한글 맞춤법 위반임에도 인지하지 못하는 경우가 많습니다.
- **규칙 3("해 주세요" 띄어쓰기):** CTA 문구에서 가장 빈번한 패턴. 보조 용언 규정을 모르면 계속 틀립니다.
- **규칙 4(조사 앞 공백):** `아이디 입니다` 류는 오탈자처럼 보여 서비스 신뢰도에 직접 영향을 줍니다.

---

### 2-3. 번역투 표현 제거

한국어 UI에서 번역투가 발생하는 이유는 두 가지입니다. 개발자가 영문 텍스트를 직역하거나, 기획자가 공문서 문체를 그대로 가져오기 때문입니다. `~의 경우`, `~을 통해`처럼 자주 쓰이지만 실제로는 어색한 표현 목록을 명시함으로써 검토자가 체크리스트로 활용할 수 있도록 했습니다.

---

### 2-4. 높임말 과용 금지

"보내드린 인증번호" 사례가 대표적입니다. 이메일·문자는 시스템이 발송한 것이므로 "드리다"는 어색합니다. 높임 표현은 **사람이 사람에게** 무언가를 할 때 씁니다. 시스템의 동작을 설명할 때 높임말을 쓰면 오히려 어색하고 과잉 공손하게 느껴집니다.

`새로운` → `새` 규칙은 별도로 불필요한 형용사 남용을 막기 위해 포함했습니다.

---

### 3-1. 버튼

이동 버튼에 `~으로`를 포함하는 규칙을 넣은 이유는 화면 이동임을 명확히 해서 사용자가 버튼을 누를 때 어디로 가는지 예측할 수 있도록 하기 위해서입니다. `다음`만으로는 "다음 단계인가, 다음 페이지인가"가 모호합니다.

확인/실행 버튼에서 `확인` 단독 사용을 제한한 이유는, 파괴적 액션(삭제, 취소, 발송)에서 `확인` 만으로는 사용자가 어떤 결과가 발생하는지 인식하지 못해 실수를 유발할 수 있기 때문입니다.

---

### 3-2. 플레이스홀더

레이블이 이미 필드 이름을 알려주고 있으므로, 플레이스홀더가 레이블과 동일한 텍스트를 반복하면 화면 공간만 낭비하고 사용자에게 추가 정보가 없습니다. 형식(예: `010-0000-0000`)이나 예시(예: `wepair`)를 제공하는 것이 입력 오류를 사전에 줄이는 실질적인 방법입니다.

---

### 3-3. 레이블

전수조사에서 같은 개념을 화면마다 다르게 표기하는 A 유형(키 불일치) 오류가 발견되었습니다. 레이블은 텍스트 자체보다 **일관성**이 신뢰감을 만듭니다. 섹션 헤더와 입력 레이블의 용어를 일치시키는 규칙을 넣은 것은 이 문제를 해결하기 위해서입니다.

---

### 3-4. 에러 메시지

에러 발생 시 사용자가 가장 먼저 알고 싶은 것은 "무엇이 잘못됐고, 어떻게 하면 되는가"입니다. "오류가 발생했습니다" 수준의 메시지는 정보를 제공하지 않으며 사용자 이탈을 유발합니다. 또한 "잘못된 입력" 같은 표현은 사용자를 탓하는 뉘앙스가 있어 브랜드 신뢰에 부정적 영향을 줍니다.

토스트 에러 제목에서 "로그인 정보 확인"보다 "로그인 실패"를 권장한 이유는, 에러 상황에서 중립적 표현은 상태를 모호하게 만들어 사용자가 성공인지 실패인지 판단하지 못하게 할 수 있기 때문입니다.

---

### 3-5. 빈상태

"데이터가 없습니다"로 끝나는 빈상태는 사용자에게 무엇을 해야 하는지 알려주지 않습니다. 특히 첫 사용자(신규 등록 후 빈 화면을 처음 보는 경우)는 서비스가 고장났다고 오해할 수 있습니다. "아직"이라는 단어를 붙이는 것은 현재 상태가 임시적이고 정상임을 암시합니다.

---

### 3-6. 알림/토스트

성공 토스트에서 `!!!`, `🎉` 같은 과도한 감탄 표현을 금지한 이유는, 위페어 파트너스가 업무 툴이기 때문입니다. 매일 반복하는 작업 완료에 과도한 축하 반응이 오면 오히려 이질적이고 유치하게 느껴집니다. Warm but composed 원칙과 직결됩니다.

---

## Q3. 보완이 필요한 부분이 있어?

솔직하게 말하면 **구조는 탄탄하지만 실무 활용 시 자주 막히는 빈틈이 있습니다.** 우선순위 순서로 정리합니다.

---

### 🔴 1순위 — 동적 변수 처리 기준이 없다

**현재 상황:** 가이드라인 전체에 변수가 포함된 문구 작성 기준이 없습니다.

실무에서는 `{차량번호} 차량의 작업을 완료했어요.` 같은 동적 문구가 필수입니다. 변수를 어떤 위치에 쓸지, 조사를 어떻게 처리할지(이/가, 을/를, 은/는 선택), 변수가 공백일 때 fallback은 무엇인지 전혀 정의되어 있지 않습니다.

**추가해야 할 내용:**
- 변수 표기 규칙 (`{변수명}` 형식 통일)
- 조사 처리 원칙 (변수 뒤 이/가 vs 은/는 처리 방식)
- 변수가 없을 때 fallback 문구 기준

---

### 🔴 1순위 — 숫자·날짜·금액 표기 기준이 없다

**현재 상황:** 가이드라인에 숫자 관련 규칙이 전혀 없습니다.

전수조사 파일을 보면 날짜 표기가 `입고 04-01`, `2024년 01월 15일 14:40`, `2026년 3월 12일 14:20`으로 혼재합니다.

**추가해야 할 내용:**
- 날짜 표기: `YYYY년 MM월 DD일` vs `MM/DD` 상황별 기준
- 시간 표기: `14:40` vs `오후 2시 40분`
- 금액 표기: 천 단위 구분자, 단위(원) 표기 방식
- 전화번호: `1660-4945` 형식 고정

---

### 🟠 2순위 — 서버 에러 처리 기준이 모호하다

**현재 상황:** `1-2. 사용 대상 및 활용 방법`에서 "서버 에러 메시지 노출 방식도 이 기준 적용"이라고 했지만, 에러 코드별 메시지 가이드가 없습니다.

개발자가 서버 에러를 처리할 때 "`500 Internal Server Error`를 사용자에게 어떻게 보여주는가"에 대한 답이 없어 개발자마다 다르게 처리할 가능성이 있습니다.

**추가해야 할 내용:**
- 공통 서버 에러 메시지 표준 (네트워크 오류, 서버 오류, 타임아웃)
- 에러 코드를 사용자에게 노출할지 여부 기준
- 기술적 오류와 사용자 입력 오류의 문구 분리 기준

---

### 🟠 2순위 — 레퍼런스 출처가 없다

**현재 상황:** 가이드라인 전체에 참고 출처가 없습니다. 팀 외부에서 검토하거나 새 팀원이 "왜 이렇게 해야 하는가"를 물었을 때 근거를 제시하기 어렵습니다.

**추가해야 할 내용:**
- 각 섹션 하단에 참고 출처 링크 또는 기준 명시
- 내부 전수조사 기반 항목과 외부 기준 기반 항목 구분

---

### 🟡 3순위 — 파괴적 액션 문구 가이드가 없다

**현재 상황:** 버튼 섹션에서 `확인` 단독 사용을 제한하지만, 삭제·취소 같은 파괴적 액션 전체에 대한 전용 가이드가 없습니다.

삭제 다이얼로그에서 Primary 버튼을 `삭제`로 할지 `삭제하기`로 할지, 확인 문구를 `삭제할까요?`로 할지 `정말 삭제하시겠어요?`로 할지 기준이 없습니다.

**추가해야 할 내용:**
- 파괴적 액션 다이얼로그 전용 구조 가이드
- Primary/Secondary 버튼 텍스트 규칙
- 되돌릴 수 없는 액션 vs 되돌릴 수 있는 액션 문구 차이

---

### 🟡 3순위 — 접근성 관련 문구 기준이 없다

**현재 상황:** 플레이스홀더 섹션에서 레이블 중복 금지를 다루지만, 접근성 관점의 문구 작성 기준은 없습니다.

스크린 리더 사용자를 위한 `aria-label`, 이미지 `alt text` 작성 기준, 아이콘 버튼의 숨김 텍스트 등이 없습니다.

**추가해야 할 내용:**
- 아이콘 전용 버튼의 숨김 레이블 작성 기준
- 이미지 alt 텍스트 작성 원칙
- 폼 필드 에러 메시지의 접근성 연결 기준

---

### 🟡 3순위 — 버전 관리 이력이 없다

**현재 상황:** 최초 작성일(2026-04-22)만 있고, 이후 변경 이력이 없습니다.

가이드라인은 살아있는 문서입니다. 원칙이 바뀌었을 때 어떤 이유로 바뀌었는지, 이전 기준은 무엇이었는지 추적할 수 없습니다.

**추가해야 할 내용:**
- 변경 이력 테이블 (`날짜 / 변경 내용 / 변경 이유`)
- 메이저 버전과 마이너 버전 구분 기준

---
